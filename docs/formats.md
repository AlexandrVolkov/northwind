# Подтверждённые форматы и границы знания

Исследован предоставленный `Horde.ISO`, метка ISO9660 `991028_1750`. Из InstallShield `SETUP/DATA1.CAB` извлечено 209 файлов, 45 073 403 байта. Исходные байты не изменяются.

## MAP2

`MAP_1.MAP`: 65 561 байт.

| Смещение | Поле | Проверка |
| --- | --- | --- |
| 0 | ASCII `MAP2` | Сигнатура |
| 4 | 13 байт имени SEG, включая NUL | `mapseg01.seg` |
| 17 | u32 LE ширина | 128 |
| 21 | u32 LE высота | 128 |
| 25 | width × height значений u32 LE, построчно | Точно заполняют остаток файла |

Младшие 16 бит клетки используются как индекс тайла: все индексы первой карты укладываются в 662 тайла, изображение местности визуально связное. Старшие 16 бит сохраняются в `map.json`; их смысл **не восстановлен**.

## SEG2

`MAPSEG01.SEG`: 700 251 байт; `n = 662`.

| Смещение | Поле |
| --- | --- |
| 0 | ASCII `SEG2` |
| 4 | u32 LE число тайлов n |
| 8–20 | 13 байт, смысл не установлен |
| 21 | n индексов палитры, используемых для миникарты |
| 21+n | n записей по 8 байт; младшие три бита первого байта используются проверкой строительства, остальные поля ещё не установлены |
| 21+9n | n растров 32×32, по одному индексу палитры на пиксель |
| 21+9n+1024n | Неинтерпретированный хвост: 16 384 байта в MAPSEG01.SEG |

Атлас и первая карта восстановлены непосредственно из этих байтов. Записи по 8 байт сохранены в `segment_properties_hex`. Хвост и непрочитанные поля не считаются ненужными: исходник требуется для дальнейшего исследования.

**Проходимость демонстрационных юнитов пока определяется эвристикой цвета миникарты**, а не оригинальными флагами столкновений: синяя область — вода, тёмно-серая — скалы, тёмно-зелёная — лес. Эвристика может ошибаться на берегах, переходах и особых тайлах. Движение сейчас четырёхсвязное, без проверки высоты/мостов/оригинальных масок.

## SPR

- u16 LE: количество записей.
- `count` относительных смещений u24 LE.
- База смещений: `2 + count * 3`.
- Последняя запись заканчивается на EOF.
- RLE: байт с установленным старшим битом задаёт `token & 127` следующих индексов палитры; без старшего бита — столько же прозрачных пикселей.

Проверено прохождение границ всех 591 записей `ARMY__00.SPR` и всех 2326 записей `ARMY__01.SPR`. Изображения дыма, молний и воина визуально распознаются. Это подтверждает способ декодирования, но не устанавливает размеры каждой записи и назначение каждого кадра.

Для прототипа используется только проверенный диапазон `ARMY__01.SPR[5:37]`: по 3844 пикселя, интерпретируется как 62×62. Первые восемь кадров используются при движении; ориентация, полный набор анимаций и их связь с DAT ещё не восстановлены. Оба лагеря пока используют один и тот же оригинальный спрайт; принадлежность обозначена цветом круга.

`COLOR1.PAL` — 768 байт, 256 RGB-троек. Цвета используются непосредственно, без умножения на 4.

## Исполняемые данные

`NORWIND.EXE` имеет SHA-256:

```
eb52f043143d763f5a595ae2175249976f278d1eebf0336ae032caf7bfa0c3a8
```

Обнаружены внешний MZ/DOS4G, BW-заголовок по смещению 62 580 и сигнатура LE по смещению 228 412. Заголовок LE сообщает CPU 2 (386), OS 1 и 55 страниц. Страницы трёх объектов теперь восстановлены статическим инструментом; релокации и полная загрузка модуля ещё не реализованы. См. [executable-analysis.md](executable-analysis.md).

REA 6.9.0, `inspect-artifact NORWIND.EXE`, подтвердил формат внешнего контейнера `dos-mz` и SHA-256. Точный ID результата: `ev_5a35cf41e20fc57723207595ae79c13f1ad62645e48b7fb39aea783c0d659d9e`.

Ограничение REA: **Inventory covers root bytes only; child container entries were not examined.** Наличие DOS-контейнера не является доказательством восстановления функций боя или ИИ.

`ARMY__*.WRK` содержит вызываемые обработчики в **32-битном x86**. Прежняя гипотеза о 16-битном режиме была неверна: префикс `67` переключает адресацию вызова через FS, а не режим исполнения обработчика. Загрузчик EXE сохраняет базу WRK, цикл объектов прибавляет поле шаблона +0x3b и выполняет near-call. Восстановлены 123 ссылки и 107 присваиваний интерфейса FS. Между инструкциями WRK есть встроенные таблицы; линейное дизассемблирование всего файла неверно интерпретирует их как код. Полная семантика обработчиков ещё не восстановлена; в игровой симуляции они пока не используются.

## SCN: структура и текстовые поля

Проверено на всех 12 `SCENA_*.SCN` из образа:

- заголовок 20 байт; байт 0 — число записей n;
- длина строго `20 + 114*n`: 932 байта для 8 записей, 1046 для 9;
- заголовок `[2:15]` — имя карты с пробелами перед точкой (`map_1   .map`);
- каждая запись: `[2:15]` — имя OBE, `[37:57]` — имя персонажа, `[94:114]` — имя поселения;
- имена CP866, дополнение `FF`; номер записи и байтовое смещение сохраняются;
- все 20 байт заголовка и все 114 байт каждой записи экспортируются в hex.

`scenario.json` содержит только эти установленные поля, размеры и SHA-256 связанных OBE. Первые строки первой карты: Олег / пос. Олега, Игорь / пос. Игоря, Эйрик / пос. Эйрика. Неизвестные байты пока не названы ресурсами, дипломатией или типами игроков.

`--audit` проверяет все цепочки SCN → MAP → SEG, все ссылки на OBE, размеры растров и индексы тайлов. Пустой OBE допустим и не считается ошибкой. `catalog.json` сохраняет результаты и полный список файлов распакованной игры с размерами и SHA-256. Аудит не устанавливает число живых игровых объектов, семантику OBE или корректность игровых правил.

## OBE: подтверждённые границы записей

У всех 97 OBE из образа цепочка разбирается до EOF без остатка: **2002 записи**. В каждой общий префикс не короче 34 байт; u32 LE по смещению +16 задаёт полную длину текущей записи. Длины различаются: например, в MAP_1_01.OBE семь записей размером 49, 49, 54, 51, 91, 49, 49 байт (сумма 392). Деление размера файла на 49 неверно.

Для проверки есть также независимое статическое наблюдение ранее выделенного кодового объекта: цикл по объектам содержит `add esi, [esi+0x10]` (смещение 0x4394 кодового объекта NORWIND.EXE). Это согласуется с использованием поля +16 как шага цепочки, но не устанавливает смысл остальных полей.

В `scenario.json` для каждого слота добавлен массив `objects`: смещение, длина, полный `raw_record_hex`, байт +0 (`raw_code`), байт +3 и u32 LE +4/+8 (`raw_x`, `raw_y`). Значения +4/+8 выглядят как координаты: почти все кратны 16 и образуют компактные группы. **Единицы, опорная точка и назначение кодов ещё не сверены с оригинальным сценарием.** Не называем эти байты типом юнита или владельцем.

Режим O в Godot показывает эти пары как маркеры с гипотезой «1 единица = 1 пиксель». N фокусирует следующую запись и показывает файл/смещение для проверки. Это диагностический просмотр, не игровая расстановка: маркеры не участвуют в симуляции, приказы и завершение хода заблокированы. Старый scenario.json без objects открывается с предложением повторить импорт.

## DAT: имена шаблонов и связь OBE → SCN → DAT

В исследованной версии шесть ARMY__*.DAT содержат 123 записи: 30, 22, 28, 37, 1 и 5. Первый u16 файла — **размер таблицы в байтах без двухбайтового заголовка**. Записи по 171 байту начинаются по смещению **2**; таблица заканчивается на `2 + table_bytes`. Это подтверждает загрузчик EXE по 0x3593–0x35a5: чтение u16, прибавление 2 к указателю, деление размера на 171. Ранее импорт ошибочно включал заголовок в первую запись и сдвигал границы всех записей на два байта; исправлено в импортёре 7.

От начала настоящей записи u32 LE по **+7** — относительный указатель от самого поля на имя CP866 с терминатором FF: `name_offset = record_offset + 7 + value`. Смещения +1/+2 — размеры изображения, +5 — кандидат базового спрайта, **+0x3b — смещение обработчика в WRK**. Имена и значения размеров/базовых спрайтов остались прежними, поскольку абсолютные позиции этих полей раньше вычислялись правильно. Исправлены file_offset, template_offset и полный raw_record_hex; теперь отдельно сохраняются raw_header_hex и raw_tail_hex. `templates.json` получил format_version=2. Общие анимации и правила всё ещё не восстановлены.

Байт OBE +0 выбирает слот таблицы армий сценария; он не обязан совпадать с номером DAT! Байт SCN +1 задаёт длину списка, в наблюдённых файлах пять номеров по +15..+19: 0,1,2,3,5. Поэтому OBE-код 4 ссылается на ARMY__05.DAT, а не ARMY__04.DAT. Байт OBE +14 выбирает запись внутри DAT.

Статическое основание: в выделенном кодовом объекте по +0x430e загружается `[esi]`, умножается на 0x56; из таблицы берётся указатель записей; по +0x4320 загружается `[esi+0x0e]` и умножается на 0xab (171). Это согласуется с наблюдёнными таблицами. Все 2002 OBE-ссылки во всех 12 сценариях укладываются в соответствующие DAT.

Пример первой записи MAP_1_01.OBE: слот 2 → ARMY__02.DAT, индекс 2 → «Замок». Остальные записи файла связываются с «Лучник», «Предводитель», «Фантом» и тремя «Ополченец». Это подтверждение ссылок и исходных имён; координаты, принадлежность, характеристики и точное отображение в игровом сценарии пока не подтверждены.

## SPR: ограниченная галерея кадров-кандидатов

В импортёре 8 добавлены шесть описаний команд на шаблон: записи по 8 байт от +0x0b, с относительной подсказкой, скан-кодом и исходным режимом. Экспортируются также используемые конструктором поля DAT[0], DAT[0x45], DAT[0x48:0x4a]. `templates.json` имеет format_version=3. [Разметка, доказательства и цепочка ремонта](building-command-lifecycle.md).

Импортёр 9 обновляет templates.json до format_version=4: construction содержит занимаемый размер DAT[3:5], маску восьми классов DAT[0x58:0x60] и четыре u32 начальной стоимости DAT[0x7c:0x8c]. По коду установлено использование младших трёх битов первого байта 8-байтовой записи свойств SEG для разрешения строительства. Остальные биты/байты и проходимость юнитов этим не восстановлены. [Проверка и ограничения](construction-payment-placement.md).

Полный строгий декодер ARMY__02.SPR отвергает часть записей (например, 1691): заявленный литеральный пробег выходит за границу записи. Это может означать другой вариант кодирования; «исправление» данных обрезанием не применяется.

Для исследовательской галереи выбирается первый строго декодируемый кадр в пределах максимум 16 записей от sprite_base_candidate и до следующей большей базы. Дополнительно требуется точное совпадение числа пикселей с шириной×высотой из DAT. Для предоставленного образа получены 72 кандидата из 123 шаблонов, 51 остаётся unresolved. Причины отклонения сохраняются в preview.rejections в templates.json. Отсутствие подходящего кадра не означает отсутствия изображения в оригинале.

Атлас template_previews.png и окно P предназначены для сравнения. Ни выбранное состояние анимации, ни направление, палитра игрока или якорь на карте этим алгоритмом не подтверждены. Совпадение размера — необходимая проверка, но не доказательство семантики кадра.
