# Сохранения оригинала (C10, в работе)

Исследован один файл `SAVE/GAME_00.SAV`, созданный оригинальной игрой в
DOSBox, **1 153 054 байт**. Сырой SAV не добавлен в Git. Его контейнер и
хеши отдельных разделов сохранены в `data/original_save_layout.json`;
`tools/save_source.py` читает произвольный файл этого формата без ISO,
сохраняет неизвестные теги и отвергает обрывы/лишний хвост. Содержимое
четырёх разделов ещё не восстановлено полностью, запись файла пока не
реализована.

## Внешний контейнер

LE:1 `F8E1..F966` открывает `save\\game_00 .sav` из LE:2 `2B8` через
DOS INT 21h/3D, читает u32 число записей, затем последовательно читает
пары `u32 length, u32 tag`. Для поиска тега сравнивается **полное dword**
`[3D0C]` с запросом; при несовпадении INT 21h/4201 пропускает `length`
байт относительно текущей позиции. Следовательно формат:

```text
u32 record_count
repeat record_count:
    u32 payload_length
    u32 tag
    byte[payload_length] payload
```

`F9DA..FA78` создаёт файл либо добавляет раздел; `F9B7..F9D9` дописывает
данные и увеличивает длину текущего раздела, `F967..F994` переписывает
его восьмибайтовый заголовок при закрытии. Для первого нового раздела
счётчик равен 1; в исследованном файле их уже 4. Это объясняет, почему
первое `0F13B5h` — **длина первого payload**, а не абсолютный адрес.
Граф участка: локальный `build/save-io-call-graph.md`. Наружу выходят
`C7AB` (копия SAV в BAK) и `10CA0` (сбор состояния); DOS INT 21h не
подменён в нативной проверке этого среза, основание здесь инструкции и
реальный файл.

| № | Заголовок | Данные | Длина | Тег |
|---:|---:|---:|---:|---:|
| 0 | 4 | 12 | 988085 | `00000011` |
| 1 | 988097 | 988105 | 25893 | `00000099` |
| 2 | 1013998 | 1014006 | 69520 | `01000022` |
| 3 | 1083526 | 1083534 | 69520 | `00010022` |

Последний раздел заканчивается **ровно** на конце файла, 1 153 054.
Теги 11h и 22h содержат в старшем слове координаты/номер области:
`FB84..FB97` берёт `[1CC7]/[1CC8]`, сдвигает на 16 и добавляет 11h;
`10573..10587` делает то же с `[1F00]/[1F01]` и 22h.
`FEC6..FED0` пишет раздел 99h с состоянием кампании. Названия
семантических полей и соответствие координат конкретным картам требуют
следующего анализа; в JSON пока только исходные числа.

`FAB4..FC62` собирает payload 11h: сначала 0F9Dh байт с данными эпизода,
затем карта видимости `[18DA]` размера `width × width`, другие блоки
terrain/объектов и списки `+56h` участников. Нельзя трактовать весь
payload как единый плоский снимок памяти: код пишет блоки разной длины.

## Где вызывается

- `9D68..9D77`: scan code 3Ch (F2) вызывает `10005`, который сначала
  копирует старый SAV в BAK (`C7AB`), затем обновляет раздел 99h
  (`FEC6`). Это подтверждено инструкциями, но не тестом реального F2.
- `9D77..9D86`: scan code 3Dh (F3) вызывает `10032`, который удаляет
  SAV, переименовывает BAK в SAV и ставит `[1EC6]=5` после успешного
  переименования. Это **откат к BAK**, а не обычная загрузка произвольного
  слота; UX и последствия пока не воспроизведены.

## Раздел 11h: сценарий и карта разведки

`FAB4..FBA7` формирует первые `0F9Dh` байт раздела. Поля `+14..+20`
содержат 13-байтное имя эпизода (`game    .epi` в образце), `+21`
копирует `[1EC5]`, `+22/+23` — байтовые ширину и высоту карты,
`+2C..+2E` — исходные `[6C6]/[6C7]/[6C8]`. С `+4Dh` на `0F50h`
байт записываются записи участников `[97A]`, так что заголовок
заканчивается точно на `+0F9Dh`.

Следом `FBAC..FBC4` пишет карту разведки `[18DA]`. **Точный код `FBB2..FBBF`
умножает width на width**, а не на height: `mov eax,[18DE]` и
`mul byte [18DE]`. В исследованном файле width=height=128, поэтому
результат 16384 байта и различие не видно по длине. Читатель
`parse_scenario11` следует инструкции и явно отвергает обрезанный блок.
После карты разведки остальные 967704 байта разделены по очереди
записи, указанной ниже; внутренние поля этих массивов остаются открытыми. Режимы игры
с прямоугольной картой по одному образцу не подтверждены.

### Остальные массивы раздела 11h

`FBC4..FC5D` продолжает запись подряд. Здесь в коде сохранены только
длины и исходные адреса; смысл полей не назначен:

| Источник в памяти | Смещение payload | Длина в образце | Формула из кода |
|---|---:|---:|---|
| `[18DA]` разведка | 3997 | 16384 | `width²` |
| `[18EE]` | 20381 | 65536 | `4×width²` |
| `[18CE]` | 85917 | 196608 | `3×4×width²` |
| `[6AA]` | 282525 | 524288 | `[6C6]×10000h` |
| `[6B6]` | 806813 | 65536 | `[6C6]×2000h` |
| `[6B2]` | 872349 | 32768 | `8000h` |
| `[6BA]` | 905117 | 53672 | `[6C8]×1A35h` |
| `[6CA]` и следующие | 958789 | 29296 всего | `[6C7]=5` списков переменной длины |

Сумма всех фиксированных частей — **958789** байт payload, остаток —
**29296**. Для переменных списков `FC4B..FC57` берёт текущие указатели
`[esi]` и `[esi+51h]`, пишет разницу и переходит к следующей записи
шагом 56h. Границы отдельных пяти списков в файле ещё не извлечены;
читатель хранит общий SHA-256 хвоста и не режет его наугад. Хеши
фиксированных массивов находятся в манифесте.

## Раздел 99h: заголовок и повторяющиеся блоки

`FEC6..FF39` пишет 25 байт с адреса `[1F45]`: `+0` = `[1972]`
(текущий участник), `+1` = dword `[1CAD]`, `+5` = dword `[1CB1]`,
`+9..+24` = 16 сырых байт `[1CB5]`. Затем ровно 512 байт из `[1CC5]`
и `0x841 × [6C9]` байт из блока по указателю `[3E87]`. Загрузка
`FF3A..FFD1` читает те же части в том же порядке и после 512 байт
вызывает `33C0`, прежде чем вычислить длину последних записей.

Читатель теперь проверяет форму раздела и сохраняет SHA-256 512-байтного
блока и каждого блока `841h`. В исследованном файле **12** последних
блоков: `25 + 512 + 12×2113 = 25893` байта, что точно совпадает с
контейнером. Значения `[1CAD]/[1CB1]/[1CB5]` оставлены с исходными
адресами: их игровой смысл пока не доказан. Раздел остаётся только
для чтения; это ещё не модель сохранения кампании Godot.

## Разделы 22h: область и контейнер объектов

`10573..10587` формирует тег из двух байтов `[1F00]/[1F01]` и
младшего слова `22h`; загрузчик `10802..10820` ищет тег таким же
образом, но из `[1CC7]/[1CC8]`. Это согласуется с двумя разделами
`01000022` и `00010022` в файле; трактовать старшее слово как порядок
X/Y без дополнительного доказательства пока нельзя.

При создании `1058F..105E7` выделяет `0F50h` байт для записей
участников, затем по `2000h` байт для каждого из `[6C6]` контейнеров
объектов и 40h байт запаса. Процедура ищет таблицу в `payload+0F50h`
и пишет туда 40h байт счётчиков `[1F45]`; реальные данные контейнеров
начинаются с `payload+0F90h` (см. расчёт `10659..10672`). В обоих
имеющихся разделах размер **69520 = 0F50h + 40h + 8×2000h**, 16
счётчиков u32 в таблице, из первых восьми только индекс 4 равен 80.
Это размещение подтверждено инструкциями и длиной файла; оставшиеся
байты контейнеров не названы объектами без разбора их внутренней схемы.

`parse_area22` сохраняет хеш префикса и каждого из восьми блоков,
проверяет длину и допустимые счётчики. Произвольные значения за пределами
числа блоков остаются в манифесте. Реальные payload не выгружаются в Git.

## Маркер завершения `66h`

Главный цикл `3221..32B9` при `[1EC6]=3` вызывает `FA79` с тегом
`66h` и сразу `F967` без промежуточного `F9B7`, поэтому вновь
созданный раздел имеет длину 0. `19C6E..19C84` для того же состояния
вызывает победный экран `1CE9A`. Комод в `196A0..19740` ищет тег
`66h` **раньше** `99h`; найденному слоту ставит `+21=4` и не читает
сводку `99h`. Отсутствие `66h` переводит поиск к обычному разделу.
Это подтверждает особый маркер победной ветки; сам образец
`GAME_00.SAV` тега `66h` не содержит. Читатель помечает тег, не
требуя нулевой длины от произвольного файла, потому что старые
перезаписанные разделы здесь не исследованы.

## Восемь слотов комода

`19668..1977F` перебирает **ровно восемь** DOS-имён
`save\game_00 .sav`…`save\game_07 .sav`: два ASCII-разряда
имени по адресу LE:2 `2B8+0Ah`, второй меняется от `30h` до `37h`.
На первом проходе ищется тег `66h`; при его наличии запись получает
состояние `+21=4`. Иначе ищется `99h`; отсутствие файла или раздела
ставит `+21=1`. После чтения `99h` сравниваются два слова окружения
`[90C9]` и `[2C2]`: совпадение ставит `+21=3`, несовпадение — `+21=2`.
Называть их «совместимая версия» без разбора этих слов преждевременно.

Для `99h` комод читает 25-байтный заголовок, затем 512-байтную таблицу.
Из таблицы **смещения 6..357** он копирует `160h=352` байта в запись
слота `A0AC+182h×i`, начиная с `+22h` (`196E1..196F9`). Это источник
части названия/сводки слота, но формат отдельных полей внутри 352 байт
ещё не доказан. `parse_session99` сохраняет хеш именно этого среза,
не превращая его в вымышленную строку. Снимок
[original-save-slots.png](reference/original-save-slots.png) показывает
восемь пустых строк комода; он не используется как подтверждение
непустого слота.
Срез `352 = 16×22` состоит из 16 записей участников. Процедура
`19811..19827` выбирает запись шагом `16h` из `A0AC+182h×slot+22h`;
первые 20 байт содержат имя CP866 до `FFh` (или пустую запись из FFh),
последние два байта пока сохраняются как сырые. В образце декодируются
**Олег, Игорь, Эйрик**, затем пустые записи. Читатель показывает эти
имена и исходные два байта без обозначения статуса/расы/владельца.

Граф участка — локальный `build/save-slots-call-graph.md`; внешние
`F8E1/F967/F995/19780` остаются за границей.
