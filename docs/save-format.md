# Сохранения оригинала (C10, в работе)

Исследован один файл `SAVE/GAME_00.SAV`, созданный оригинальной игрой в
DOSBox, **1 153 054 байт**. Сырой SAV не добавлен в Git. Его контейнер и
хеши отдельных разделов сохранены в `data/original_save_layout.json`;
`tools/save_source.py` читает произвольный файл этого формата без ISO,
сохраняет неизвестные теги и отвергает обрывы/лишний хвост. Содержимое
четырёх разделов ещё не восстановлено полностью, запись файла пока не
реализована.

## Внешний контейнер

LE:1 `F8E1..F966` открывает `save\\game_00 .sav` из LE:2 `2B8` через
DOS INT 21h/3D, читает u32 число записей, затем последовательно читает
пары `u32 length, u32 tag`. Для поиска тега сравнивается **полное dword**
`[3D0C]` с запросом; при несовпадении INT 21h/4201 пропускает `length`
байт относительно текущей позиции. Следовательно формат:

```text
u32 record_count
repeat record_count:
    u32 payload_length
    u32 tag
    byte[payload_length] payload
```

`F9DA..FA78` создаёт файл либо добавляет раздел; `F9B7..F9D9` дописывает
данные и увеличивает длину текущего раздела, `F967..F994` переписывает
его восьмибайтовый заголовок при закрытии. Для первого нового раздела
счётчик равен 1; в исследованном файле их уже 4. Это объясняет, почему
первое `0F13B5h` — **длина первого payload**, а не абсолютный адрес.
Граф участка: локальный `build/save-io-call-graph.md`. Наружу выходят
`C7AB` (копия SAV в BAK) и `10CA0` (сбор состояния); DOS INT 21h не
подменён в нативной проверке этого среза, основание здесь инструкции и
реальный файл.

| № | Заголовок | Данные | Длина | Тег |
|---:|---:|---:|---:|---:|
| 0 | 4 | 12 | 988085 | `00000011` |
| 1 | 988097 | 988105 | 25893 | `00000099` |
| 2 | 1013998 | 1014006 | 69520 | `01000022` |
| 3 | 1083526 | 1083534 | 69520 | `00010022` |

Последний раздел заканчивается **ровно** на конце файла, 1 153 054.
Теги 11h и 22h содержат в старшем слове координаты области:
`FB84..FB97` берёт `[1CC7]/[1CC8]`, сдвигает на 16 и добавляет 11h;
`10573..10587` делает то же с `[1F00]/[1F01]` и 22h.
`FEC6..FED0` пишет раздел 99h с состоянием кампании. `103EC..1040B`
проверяет, что `CL < [1CC5]` и `CH < [1CC6]`, и сохраняет `CL/CH` в
`[1F00]/[1F01]` перед созданием 22h; `10799..107E3` сначала прибавляет
их к текущим `[1CC7]/[1CC8]`. Значит младший байт старшего слова
тега — X, старший — Y. В образце 11h относится к (0,0), а два 22h —
к (0,1) и (1,0). Соответствие этих координат названиям карт ещё
требует разбора эпизода.

`FAB4..FC62` собирает payload 11h: сначала 0F9Dh байт с данными эпизода,
затем карта видимости `[18DA]` размера `width × width`, другие блоки
terrain/объектов и банки TRE. Нельзя трактовать весь
payload как единый плоский снимок памяти: код пишет блоки разной длины.

## Где вызывается

- `9D68..9D77`: scan code 3Ch (F2) вызывает `10005`, который сначала
  копирует старый SAV в BAK (`C7AB`), затем обновляет раздел 99h
  (`FEC6`). Это подтверждено инструкциями, но не тестом реального F2.
- `9D77..9D86`: scan code 3Dh (F3) вызывает `10032`, который удаляет
  SAV, переименовывает BAK в SAV и ставит `[1EC6]=5` после успешного
  переименования. Это **откат к BAK**, а не обычная загрузка произвольного
  слота; UX и последствия пока не воспроизведены.

## Раздел 11h: сценарий и карта разведки

`FAB4..FBA7` формирует первые `0F9Dh` байт раздела. Поля `+14..+20`
содержат 13-байтное имя эпизода (`game    .epi` в образце), `+21`
копирует `[1EC5]`, `+22/+23` — байтовые ширину и высоту карты,
`+2C..+2E` — исходные `[6C6]/[6C7]/[6C8]`. С `+4Dh` на `0F50h`
байт записываются записи участников `[97A]`, так что заголовок
заканчивается точно на `+0F9Dh`.

Поля `+24h/+28h` пишутся из `[190E]/[1912]`. Загрузчик
`FCCC..FCEC` восстанавливает их и кладёт значения, сдвинутые вправо
на 5 бит, в `[1906]/[190A]`. В образце это `480/1152` и `15/36`;
назначение координат здесь не объявлено без трассы вызывающего кода.

`0F50h = 16×0F5h`: заголовок содержит 16 записей участников.
Загрузчик `FDA2..FDD0` читает этот блок, но при копировании обратно в
`[97A]` пропускает первые **9 байт каждой записи** и копирует следующие
`0ECh`; начальные девять байт остаются от уже загруженного эпизода.
Затем `FDD0..FDF7` берёт из записи текущего участника три dword по
`+18h/+1Ch/+20h`, прибавляет к каждому 1 и кладёт в `[1C62]/[1C66]/[1C6A]`.
В образце у участника 0 сохранены `1976/1976/0`; названия трёх
ресурсных балансов в другом исследовании ещё не установлены. Манифест
сохраняет для каждой записи адрес, хеш всей записи и девятибайтного
префикса, а также три значения без вымышленных названий.

Следом `FBAC..FBC4` пишет карту разведки `[18DA]`. **Точный код `FBB2..FBBF`
умножает width на width**, а не на height: `mov eax,[18DE]` и
`mul byte [18DE]`. В исследованном файле width=height=128, поэтому
результат 16384 байта и различие не видно по длине. Читатель
`parse_scenario11` следует инструкции и явно отвергает обрезанный блок.
После карты разведки остальные 967704 байта разделены по очереди
записи, указанной ниже; внутренние поля этих массивов остаются открытыми. Режимы игры
с прямоугольной картой по одному образцу не подтверждены.

### Остальные массивы раздела 11h

`FBC4..FC5D` продолжает запись подряд. Здесь в коде сохранены только
длины и исходные адреса; смысл полей не назначен:

| Источник в памяти | Смещение payload | Длина в образце | Формула из кода |
|---|---:|---:|---|
| `[18DA]` разведка | 3997 | 16384 | `width²` |
| `[18EE]` | 20381 | 65536 | `4×width²` |
| `[18CE]` | 85917 | 196608 | `3×4×width²` |
| `[6AA]` | 282525 | 524288 | `[6C6]×10000h` |
| `[6B6]` | 806813 | 65536 | `[6C6]×2000h` |
| `[6B2]` | 872349 | 32768 | `8000h` |
| `[6BA]` | 905117 | 53672 | `[6C8]×1A35h` |
| `[6CA]` и следующие | 958789 | 29296 всего | `[6C7]=5` банков TRE, по 16 копий |

Сумма всех фиксированных частей — **958789** байт payload, остаток —
**29296**. Для переменных списков `FC4B..FC57` берёт текущие указатели
`[esi]` и `[esi+51h]`, пишет разницу и переходит к следующей записи
шагом 56h. Инициализация `35D0..362C` читает из `ARMY__NN.TRE` 16
копий в память, начиная с `[esi+51h]`; указатель `[esi]` ставится
после них, перед чтением `ARMY__NN.SPR`. Поэтому записываемая разница
равна **16×размер файла TRE**, а не длине произвольного списка.
В образце пять банков соответствуют файлам `ARMY__00..04.TRE`:

| Банк | TRE-файл | Длина в 11h | Смещение в payload |
|---:|---:|---:|---:|
| 0 | 632 | 10112 | 958789 |
| 1 | 404 | 6464 | 968901 |
| 2 | 759 | 12144 | 975365 |
| 3 | 18 | 288 | 987509 |
| 4 | 18 | 288 | 987797 |

Сумма — **29296**, последний байт заканчивает payload на 988085.
`parse_scenario11` принимает эти размеры *необязательным* параметром:
без исходных TRE общий хвост остаётся доступен по хешу, а с размерами
появляются границы и хеши каждого банка. Формат TRE уже разобран в
[tech.md](tech.md); хеши фиксированных массивов и
банков находятся в манифесте.

Если указать каталог с оригинальными TRE через `--tree-dir`, читатель
сравнивает 16 копий каждого банка с соответствующим исходным файлом.
В данном SAV **78 из 80** копий совпадают побайтно. Отличаются только
копия 11 банка 1 (7 байт) и копия 12 банка 2 (18 байт). Манифест
хранит лишь хеши, число изменённых байтов и значения изменённых полей,
не сырые TRE. Все 25 изменений относятся к двум полям записи дерева:
`+0` (бит завершения) или `+2` (число невыполненных условий). Сводка
получена существующим декодером `tech_source.py`; иных изменённых
смещений в образце нет. Это подтверждает сохранение состояния
исследований каждого участника и согласуется с указателем на копию
TRE в [tech.md](tech.md). Причину конкретного прогресса в этом SAV
без истории партии восстановить нельзя.

## Раздел 99h: заголовок и повторяющиеся блоки

`FEC6..FF39` пишет 25 байт с адреса `[1F45]`: `+0` = `[1972]`
(текущий участник), `+1` = dword `[1CAD]`, `+5` = dword `[1CB1]`,
`+9..+24` = 16 сырых байт `[1CB5]`. Затем ровно 512 байт из `[1CC5]`
и `0x841 × [6C9]` байт из блока по указателю `[3E87]`. Загрузка
`FF3A..FFD1` читает те же части в том же порядке и после 512 байт
вызывает `33C0`, прежде чем вычислить длину последних записей.

Читатель теперь проверяет форму раздела и сохраняет SHA-256 512-байтного
блока и каждого блока `841h`. В исследованном файле **12** последних
блоков: `25 + 512 + 12×2113 = 25893` байта, что точно совпадает с
контейнером. Значения `[1CAD]/[1CB1]/[1CB5]` оставлены с исходными
адресами: их игровой смысл пока не доказан. Раздел остаётся только
для чтения; это ещё не модель сохранения кампании Godot.

Каждый блок `841h = 1 + 16×84h`. На экране карты похода код
`1A14E..1A21F` проверяет бит 0 первого байта блока, затем обращается
к записи участника с шагом `84h`; в проверке `[ebp+17h]` и
`[ebp+84h×текущий_участник+1]` тоже видно это деление. В образце
первый блок начинается с `01h`, остальные 11 — с `00h`.
`parse_session99` хранит первый байт и хеш каждой из 16 вложенных
записей. Бит 0 связан с отрисовкой карты похода, но остальные биты и
поля участника ещё не названы. 12 блоков не следует автоматически
считать 12 игровыми картами: соответствие экрану переходов требует
отдельного исследования.

## Разделы 22h: область и контейнер объектов

`10573..10587` формирует тег из двух байтов `[1F00]/[1F01]` и
младшего слова `22h`; загрузчик `10802..10820` ищет тег таким же
образом, но из `[1CC7]/[1CC8]`. Это согласуется с двумя разделами
`01000022` и `00010022` в файле. Их координаты теперь подтверждены
проверкой границ и присваиваниями `103EC..1040B`: (0,1) и (1,0).

При создании `1058F..105E7` выделяет `0F50h` байт для записей
участников, затем по `2000h` байт для каждого из `[6C6]` контейнеров
объектов и 40h байт запаса. Процедура ищет таблицу в `payload+0F50h`
и пишет туда 40h байт счётчиков `[1F45]`; реальные данные контейнеров
начинаются с `payload+0F90h` (см. расчёт `10659..10672`). В обоих
имеющихся разделах размер **69520 = 0F50h + 40h + 8×2000h**, 16
счётчиков u32 в таблице, из первых восьми только индекс 4 равен 80.
Это размещение подтверждено инструкциями и длиной файла; оставшиеся
байты контейнеров не названы объектами без разбора их внутренней схемы.

`parse_area22` сохраняет хеш префикса и каждого из восьми блоков,
проверяет длину и допустимые счётчики. Произвольные значения за пределами
числа блоков остаются в манифесте. Реальные payload не выгружаются в Git.

Код добавления объекта `10611..1067C` увеличивает счётчик байтов
`[1F45+4×bucket]` на размер записи `[edi]`, затем вычисляет позицию
записи как `0F90h + (bucket+1)×2000h − новый_счётчик`. Значит занятая
область каждого bucket растёт **с конца назад**. Читатель теперь
сохраняет хеш и число ненулевых байтов только последнего `count`-среза,
параллельно с хешем полного блока. В обоих образцах лишь bucket 4 имеет
`count=80`; в его последних 80 байтах соответственно 25 и 27 ненулевых.
За объявленной областью в других bucket тоже встречаются ненулевые
байты, поэтому считать весь 2000h-блок занятыми объектами нельзя.
Первые `0F50h` байт обоих 22h-разделов нулевые и не совпадают с 16
непустыми записями участников раздела 11h; в данном образце эти две
области не содержат снимок состояния участников.

Загрузчик области `10802..108CD` раскрывает назначение первых `0F50h`
байт: это **отложенные переводы** для 16 участников, каждый по `0F5h`.
Для текущего `[1972]` он прибавляет три dword `+18h/+1Ch/+20h` к
соответствующим счётчикам `[97A]`, а каждое ненулевое значение из 20
байт `+CDh..+E0h` переносит в первый свободный такой же слот записи
участника. После переноса он заменяет свою `0F5h`-запись в SAV нулями
(`108A0..108C8`). Это одноразовое поглощение накопленного состояния
области, а не простое копирование поверх текущего игрока. В двух
имеющихся разделах все 16 записей равны нулю; читатель теперь отдельно
сохраняет тройки счётчиков и хеши 20-байтных наборов, чтобы будущие
непустые сохранения были сопоставимы. Значения этих двадцати байтов
пока не названы предметами или технологиями без проверки источников.

Следом `108D7..109EF` читает таблицу счётчиков и полный блок `2000h`
для каждого непустого bucket, начинает обход с `конец_блока−count`
и продвигается на размер шаблона объекта `[edi]`. После обработки
`109F5..10A19` **обнуляет все 16 счётчиков в SAV**. Загрузка области
потребляет как отложенные переводы участника, так и записи объектов.
Успех каждого объекта зависит от внешних проверок `6885`, `10AD2`,
`A758`; без них нельзя утверждать, что все сохранённые объекты
восстановятся. Читатель остаётся только для анализа и ничего не обнуляет.

Шаг обхода можно проверить по реальному DAT: `6885..689F` выбирает
армию из байта записи `+0`, шаблон из `+0Eh` и читает размер из
`DAT[2 + 0ABh×шаблон]` (первые два байта DAT пропускаются загрузчиком
`3593..359C`). В этом SAV оба суффикса bucket 4 содержат ровно **две
записи по 40 байт**: армия 0, шаблон 0 («Лагерь» по
`assets/imported/templates.json`), байт `+3` равен 4.
Командный `save_source.py` берёт размеры из уже включённого в проект
`assets/imported/templates.json` и сохраняет границы/хеши без DAT или
ISO. Параметр `--dat-dir` позволяет повторить разбор по исходным DAT;
оба пути дали **одинаковый манифест** для образца. Если каталог
шаблонов недоступен, суффикс остаётся непрозрачным. Поле `+10h`
в этих сохранённых записях не является надёжной длиной (первое значение
равно 2107), поэтому применять к ним правило дискового OBE о длине
`+10h` нельзя. Координаты этих лагерей и результат попытки
восстановления ещё не проверены.

## Маркер завершения `66h`

Главный цикл `3221..32B9` при `[1EC6]=3` вызывает `FA79` с тегом
`66h` и сразу `F967` без промежуточного `F9B7`, поэтому вновь
созданный раздел имеет длину 0. `19C6E..19C84` для того же состояния
вызывает победный экран `1CE9A`. Комод в `196A0..19740` ищет тег
`66h` **раньше** `99h`; найденному слоту ставит `+21=4` и не читает
сводку `99h`. Отсутствие `66h` переводит поиск к обычному разделу.
Это подтверждает особый маркер победной ветки; сам образец
`GAME_00.SAV` тега `66h` не содержит. Читатель помечает тег, не
требуя нулевой длины от произвольного файла, потому что старые
перезаписанные разделы здесь не исследованы.

## Восемь слотов комода

`19668..1977F` перебирает **ровно восемь** DOS-имён
`save\game_00 .sav`…`save\game_07 .sav`: два ASCII-разряда
имени по адресу LE:2 `2B8+0Ah`, второй меняется от `30h` до `37h`.
На первом проходе ищется тег `66h`; при его наличии запись получает
состояние `+21=4`. Иначе ищется `99h`; отсутствие файла или раздела
ставит `+21=1`. После чтения `99h` сравниваются два слова окружения
`[90C9]` и `[2C2]`: совпадение ставит `+21=3`, несовпадение — `+21=2`.
Называть их «совместимая версия» без разбора этих слов преждевременно.

Для `99h` комод читает 25-байтный заголовок, затем 512-байтную таблицу.
Из таблицы **смещения 6..357** он копирует `160h=352` байта в запись
слота `A0AC+182h×i`, начиная с `+22h` (`196E1..196F9`). Это источник
части названия/сводки слота, но формат отдельных полей внутри 352 байт
ещё не доказан. `parse_session99` сохраняет хеш именно этого среза,
не превращая его в вымышленную строку. Снимок
[original-save-slots.png](reference/original-save-slots.png) показывает
восемь пустых строк комода; он не используется как подтверждение
непустого слота.
Срез `352 = 16×22` состоит из 16 записей участников. Процедура
`19811..19827` выбирает запись шагом `16h` из `A0AC+182h×slot+22h`;
первые 20 байт содержат имя CP866 до `FFh` (или пустую запись из FFh),
последние два байта пока сохраняются как сырые. В образце декодируются
**Олег, Игорь, Эйрик**, затем пустые записи. Читатель показывает эти
имена и исходные два байта без обозначения статуса/расы/владельца.

Запущенный оригинал с этим же локальным `GAME_00.SAV` показал в первой
строке «Игра 0», а справа **Олег, Игорь, Эйрик**. Остальные семь строк
показывают «Новая игра». Снимок
[original-save-occupied.png](reference/original-save-occupied.png) подтверждает,
что декодированные имена действительно попадают в комод.

Подпись теперь прослежена до LE:1 `1B5FE..1B650`, обратного вызова
виджета. При `AL=2` процедура берёт номер слота из `widget+15h`,
преобразует его в ASCII-цифру (`+30h`) и заменяет шестой байт строки
LE:3 `9FE5` «Игра 0». Состояния слота `+21h=2` и `3` выбирают эту
строку; `4` выбирает LE:3 `9FF7` «Игра окончена»; остальные — LE:3
`9FEC` «Новая игра». `1C3C0` передаёт выбранный указатель в функцию
вывода текста `6CD6`. Вспомогательная функция `cabinet_slot_caption`
в `tools/save_source.py` повторяет это правило для анализа сохранений.
Реальный снимок подтверждает сочетание состояния 3, индекса 0 и трёх
имён; состояние 4 визуально пока не проверено.
