# Сохранения оригинала (C10, в работе)

Исследован один файл `SAVE/GAME_00.SAV`, созданный оригинальной игрой в
DOSBox, **1 153 054 байт**. Сырой SAV не добавлен в Git. Его контейнер и
хеши отдельных разделов сохранены в `data/original_save_layout.json`;
`tools/save_source.py` читает произвольный файл этого формата без ISO,
сохраняет неизвестные теги и отвергает обрывы/лишний хвост. Содержимое
четырёх разделов ещё не восстановлено полностью, запись файла пока не
реализована.

## Внешний контейнер

LE:1 `F8E1..F966` открывает `save\\game_00 .sav` из LE:2 `2B8` через
DOS INT 21h/3D, читает u32 число записей, затем последовательно читает
пары `u32 length, u32 tag`. Для поиска тега сравнивается **полное dword**
`[3D0C]` с запросом; при несовпадении INT 21h/4201 пропускает `length`
байт относительно текущей позиции. Следовательно формат:

```text
u32 record_count
repeat record_count:
    u32 payload_length
    u32 tag
    byte[payload_length] payload
```

`F9DA..FA78` создаёт файл либо добавляет раздел; `F9B7..F9D9` дописывает
данные и увеличивает длину текущего раздела, `F967..F994` переписывает
его восьмибайтовый заголовок при закрытии. Для первого нового раздела
счётчик равен 1; в исследованном файле их уже 4. Это объясняет, почему
первое `0F13B5h` — **длина первого payload**, а не абсолютный адрес.
Граф участка: локальный `build/save-io-call-graph.md`. Наружу выходят
`C7AB` (копия SAV в BAK) и `10CA0` (сбор состояния); DOS INT 21h не
подменён в нативной проверке этого среза, основание здесь инструкции и
реальный файл.

| № | Заголовок | Данные | Длина | Тег |
|---:|---:|---:|---:|---:|
| 0 | 4 | 12 | 988085 | `00000011` |
| 1 | 988097 | 988105 | 25893 | `00000099` |
| 2 | 1013998 | 1014006 | 69520 | `01000022` |
| 3 | 1083526 | 1083534 | 69520 | `00010022` |

Последний раздел заканчивается **ровно** на конце файла, 1 153 054.
Теги 11h и 22h содержат в старшем слове координаты/номер области:
`FB84..FB97` берёт `[1CC7]/[1CC8]`, сдвигает на 16 и добавляет 11h;
`10573..10587` делает то же с `[1F00]/[1F01]` и 22h.
`FEC6..FED0` пишет раздел 99h с состоянием кампании. Названия
семантических полей и соответствие координат конкретным картам требуют
следующего анализа; в JSON пока только исходные числа.

`FAB4..FC62` собирает payload 11h: сначала 0F9Dh байт с данными эпизода,
затем карта видимости `[18DA]` размера `width × height`, другие блоки
terrain/объектов и списки `+56h` участников. Нельзя трактовать весь
payload как единый плоский снимок памяти: код пишет блоки разной длины.

## Где вызывается

- `9D68..9D77`: scan code 3Ch (F2) вызывает `10005`, который сначала
  копирует старый SAV в BAK (`C7AB`), затем обновляет раздел 99h
  (`FEC6`). Это подтверждено инструкциями, но не тестом реального F2.
- `9D77..9D86`: scan code 3Dh (F3) вызывает `10032`, который удаляет
  SAV, переименовывает BAK в SAV и ставит `[1EC6]=5` после успешного
  переименования. Это **откат к BAK**, а не обычная загрузка произвольного
  слота; UX и последствия пока не воспроизведены.
