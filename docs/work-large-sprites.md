# Крупные записи WORK.SPR: данные для Claude (C5)

Размеры восстановлены для **59 из 60** записей очереди C5. Запись 358 пока
остаётся открытой: потребитель и исходный размер не найдены. Поэтому C5
сохраняет статус «в работе». Закреплённые `interface_source.py`,
`assets/imported/interface/` и `docs/interface.md` не менялись.

## Разные кодировки в одном SPR

227..230 и 315..357 — **RAW, один байт палитры на пиксель**. Попытка разобрать
их стандартными SPR-прогонами даёт бессмысленную длину. В группе меню LE:3
`3E8F` записи виджетов по 1Eh байт, тип 80h (младший тип 0): `u16 +12`
— ширина, `u16 +14` — высота, `+16=FFh` выбирает WORK, `u16 +17` — кадр.
LE:1 `E12B..E18E` выбирает запись через `1E133`; `E161/E165` читают размеры.
При `+10=8` (все выгруженные RAW-виджеты) вызов **E17D→1DF08** копирует
индексы напрямую; другой стиль использует E184→1DF3C с таблицей цветов.
Прозрачность RAW-нулю не приписывается.

388..399 — SPR RLE. Группа LE:3 **46DA**, размер 120 байт, четыре виджета
типа 85h: `+12/+13` — байтовые размеры, `+14=FFh`, `u16 +15` — относительный
кадр 0..3. Инициализатор **127E9..12813** прибавляет `388 + 4*selector`
к четырём кадрам и задаёт верхним y=аргумент EBX, нижним y=EBX+240.
12814..1284B перебирает три бита/три варианта и создаёт эти группы через DEE4;
DEE4 вызывает инициализатор из заголовка группы (`DF1E`).
Вывод типа 5: **E267..E2A4**, размеры E29D/E2A0, **E2A4→1E153**.

Точный callback каждой записи присутствует в манифесте. В двух обычных
состояниях виджет обычно хранит чётный кадр, 111C5 при event=1 уменьшает его
на единицу. «Реверс» и «Тест» имеют собственные правила, их нельзя объявить
теми же двумя состояниями только по соседству картинок.

Виджеты рукописей расположены двумя колонками x=−31 и x=224. Четыре тайла
образуют 510×480 до обрезки картовым рисовальщиком; это три разных текстовых
свитка, не последовательность из двенадцати кадров анимации. На первом
читаются сведения о кристаллах и посохах. Полный игровой сценарий их открытия
не перенесён и здесь не объявляется проверенным.

## Проверка и выгрузка

`tools/work_sprite_source.py` проверяет SHA-256 EXE, тип/банк/стиль виджетов,
их размер и исходный номер, форму инициализатора рукописей, затем сохраняет
59 PNG и подробный манифест в `assets/imported/work_large/`. В исходный
конвертер интерфейса изменения не вносятся.

На настоящем DOSBox 13 RAW-прямоугольников совпали целиком с PNG: «Меню» и
«Дипломатия» на `original-help-00.png`, ещё 11 элементов панели на
`docs/reference/original-work-menu-panel.png`. Курсор перед снимком убран
из проверяемых областей. Цвет — COLOR1 с квантованием VGA DAC. Python
повторяет эти сравнения и проверяет все размеры/хеши, отдельно различая
непрозрачный RAW и прозрачные SPR-прогоны.

Дополнительно `verify_work_sprites.py` исполняет реальные 1DF08/1E098 для
всех 59 записей. Для RLE два разных фона независимо определяют прозрачные
прогоны. Все RGBA совпали с конвертером; C#-режим `work-sprites` повторяет
эти хеши по подготовленным PNG. Dirty-helper 3EEA подменён пустым возвратом,
отрисовка и шаг framebuffer 640 исполняются оригинальные. Обрезка 1E153 и
полный UI-диспетчер этим oracle не проверяются.

```sh
python tools/work_sprite_source.py --game /path/to/Program_Executable_Files
python tools/verify_work_sprites.py --game /path/to/Program_Executable_Files --fixture /tmp/work-sprites.json
godot --headless --path . tests/TestRunner.tscn -- work-sprites
python -m unittest discover -s tests -p 'test_*.py'
```

Пункты для продолжения C5:

- Найти потребителя 358 либо обоснованно классифицировать запись как остаток
  неиспользуемой реализации. Текущие полосы ползунков — виджеты типа 0Ch,
  а не автоматическое доказательство использования этой картинки.
- В задаче упомянут 1E4F0. По фактическому входу это выделение памяти
  участникам (`movzx ebx,[6C6]; mov eax,1A35h; mul ebx; ... int31h`), не
  графический blit. Линейная распечатка зацепила его начало после нулевого
  выравнивания с неправильной границы; проверять от известного входа Capstone.
