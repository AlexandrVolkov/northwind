# Продолжение переноса в новой сессии

Этот файл фиксирует состояние репозитория после PR #36. Актуальный код — ветка `main` в `AlexandrVolkov/northwind`. Сначала прочитайте [AGENTS.md](../AGENTS.md), [план](port-plan.md), [карту логики](game-logic-map.md) и [реестр покрытия ассемблера](assembly-progress.md). Перед изменениями выполните `git pull --ff-only` и проверьте `git status`.

## Цель и договорённости

- Перенести «Орду: Северный ветер» целиком на **Godot 4.7.2 .NET / C# и .NET 10 LTS**, оставив понятную структуру для модификаций. Различать правила, подтверждённые исходными машинными инструкциями и ресурсами, сведения игрока и временные правила опытной схватки.
- Пользователь работает на Windows 11. Подготовленные изображения, первая карта, сценарий и таблицы уже лежат в `assets/imported`; для **запуска текущей версии** не нужен ISO, Python или повторный импорт. Нужны .NET-сборка Godot и SDK 10. Оригинальный ISO нужен только для нового исследования или подготовки других ресурсов.
- Пользователь ранее разрешил создавать PR и сливать готовые проверенные изменения в `main`. Предпочтителен законченный, проверяемый игровой срез за PR. В Git нельзя добавлять исходный ISO, NORWIND.EXE, DAT/WRK, их побайтовые листинги, локальные SQLite-базы анализа и кэши.

## Что уже есть

Текущий запуск — **экспериментальная схватка на первой карте**, не кампания. В ней есть исходная расстановка выбранных отрядов, групповые приказы, движение с несколькими перенесёнными ядрами, временные бой и ИИ, поражение при смерти героя. Работают рабочие, лес и доставка древесины в лесопилку, фермы и прирост людей, строительство казарм и независимые очереди ополченцев. Шахта строится по DAT, определяет тип и начальный запас руды по MAP/WRK/EXE; **добыча, мешки, доставка и зачисление металла или золота ещё не работают**. Текущие границы описаны в [схватке](playable-skirmish.md), [найме](recruitment-production.md) и [шахтах](mine-deposits.md).

`data/skirmish.json` содержит временные здоровье, бой, частоту тактов и состав миссии. Не выдавайте эти величины за исходный баланс. `data/reverse_engineering/annotations.json` — редактируемый реестр исследованных диапазонов; `docs/assembly-coverage.json` и `docs/assembly-progress.md` показывают пробелы. Фикстуры `tests/fixtures` хранят входы и результаты сравнений, а не оригинальный код.

## Следующий игровой срез: добыча руды

1. Проследить путь **шахта → рабочий с грузом 1/2 → получатель → запас участника** до конкретных смещений полей и условий. Пока нельзя утверждать, какой из типов 1/2 означает золото, а какой металл. Слова игрока о переносе мешков в замок — ориентир для проверки, не замена кода.
2. Уже подтверждено: `ARMY__02.WRK+0x524` — вход шахты; `+0x5D6..0x61E` выбирает тип и начальный запас. `LE:1 0xB3F7..0xB47F` считает клетки руды 3×3; C# реализация — `scripts/OriginalMineRules.cs`, проверка — `tools/verify_mine_deposits.py` и 108 случаев в `tests/fixtures/mine-deposits.json`.
3. Исследовать `LE:1 0xB47F..0xB502`: ожидание рабочего, вызов его обработчика, уменьшение запаса на 100 и шаг истощения рудной карты. Для груза посмотреть `ARMY__02.WRK+0x851..0x8EA`: при кодах 1/2 рабочий переключается на шаблон 8; лесной груз 3 уже перенесён отдельно. Изолировать операции и сверить их с настоящими инструкциями x86 до включения в игровой цикл.
4. Найти и проверить обработчик сдачи груза и зачисления конкретного ресурсного слота. Включить движение рабочего, ожидание входа, потерю получателя и несколько грузов. Проверить путь от обычного SCN-старта: ферма → люди → шахта и рабочий → ресурс → расход на новое здание.

Локальный анализ предыдущих сессий находился в `build/assembly-final/assembly.sqlite` и `build/rea-assembly-initial/`, но эти папки игнорируются Git и **не будут доступны в новой чистой копии**. Их можно восстановить из собственной установленной игры/ISO по [инструкции для базы](assembly-database.md). Для игры и большинства тестов они не нужны. Профили SHA-256, доказательства и пометки уже в Git; адреса `LE:1` относятся к первому LE-объекту, а `WRK` — к началу указанного файла. Не смешивайте эти пространства адресов.

## Быстрая проверка

Из корня репозитория, с установленными SDK 10 и **Godot 4.7.2 mono**:

```sh
dotnet build
godot --headless --editor --path . --quit-after 120
godot --headless --path . tests/TestRunner.tscn -- simulation
godot --headless --path . tests/TestRunner.tscn -- scene
godot --headless --path . tests/TestRunner.tscn -- mine
python -m unittest discover -s tests -p 'test_*.py'
```

Здесь `godot` означает .NET-сборку точной версии; при другом имени команды укажите полный путь. Дополнительные режимы `production`, `population`, `economy` проверяют связанные хозяйственные циклы. Графические изменения проверяйте в оконном режиме. Если меняется конвертер или отслеживаемый атлас, проверьте также импорт и сцену из **чистой копии отслеживаемых файлов**. Исследовательские генераторы фикстур требуют оригинальных файлов и Python-зависимостей из `tools/requirements-research.txt`; запуск схватки их не требует.

При обновлении пометок ассемблера синхронизируйте отчёт по [инструкции](assembly-database.md), затем фиксируйте `annotations.json`, `assembly-coverage.json` и `assembly-progress.md` вместе. Указывайте границы проверенного участка и оставшиеся неизвестные ветви: пометка `ported` для одной операции не означает, что перенесён весь обработчик.
