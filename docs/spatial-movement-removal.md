# Шаг движения и отсоединение записи по EXE

[OriginalSpatialRules.cs](../scripts/OriginalSpatialRules.cs) продолжает [перенос занятости](original-occupancy.md). Перенесены ограниченная фаза движения **71F5..725C** с настоящим обработчиком переноса прямоугольников **9B0D..9B85** и полностью функция отсоединения **98CC..996E**. Проверка использует исполнение исходного x86, без подмены внутренних вызовов.

## Движение внутри выбранного шага

Внешний обработчик выбирает маршрут, направление и параметр движения до этого участка. Новая функция принимает уже подготовленную запись. Она не планирует путь, не проверяет столкновения и не получает delta из Godot.

Байт **OBE[0x26]** здесь содержит упакованное значение с накоплением дробной части; его нельзя просто назвать числом пикселей за кадр. Для исходного значения `v`:

```text
sum = v + u8(v << 6)
OBE[0x26] = u8(sum)
distance = ((v >> 2) + carry(sum)) & 15
distance = min(distance, OBE[0x2c])
OBE[0x2c] -= distance
```

Флаг по глобальному **1C9F** изменяется маской BF. C# возвращает это значение в OriginalMotionStep, вместе с расстоянием и признаком переноса занятости. Остальные глобальные игровые состояния этот метод не моделирует.

Если оставшееся расстояние пересекает порог **16** сверху вниз (`old >= 16`, `new < 16`), вызывается 9B0D. Он использует направление **(OBE[0x25] >> 3) & 7** и оставшееся расстояние уже после уменьшения:

```text
old_rectangle_center = current_position - direction × (32 - new_remaining)
new_rectangle_center = current_position + direction × new_remaining
```

Первый прямоугольник безусловно очищается, второй безусловно заполняется относительной ссылкой самого объекта. После этого координаты изменяются на `distance` по направлению **OBE[0x25] & 7**. Верхняя и нижняя тройки битов могут различаться; перенос не отождествляет их.

Таблица из **DS:19C7**, объект LE № 2, задаёт восемь направлений: вверх, вверх-вправо, вправо, вниз-вправо, вниз, вниз-влево, влево, вверх-влево. Это исходные числовые направления, а не подбор по спрайтам. Координата Y растёт вниз. Арифметика координат сохраняет переполнение u32. При переносе обе области должны целиком лежать в карте и использовать одну из трёх плоскостей; C# проверяет обе до изменения сетки/записи. Выход за этот пространственный профиль отклоняется, а нативный писатель границы не проверяет.

Остановка проверки по **725C** находится перед анимацией, эффектами и завершением действия. Неподтверждённая частота тактов, расчёт скорости из DAT/SEG, поиск пути, поворот, отмена и специальные варианты движения здесь не перенесены. В частности, отдельный участок **9A97..9B0C** имеет другую логику; на него данный API не распространяется.

## Отсоединение из цепочки владельца

Функция 98CC очищает текущую область только если в **u16 OBE[0x17]** отсутствует бит **80**. Проверки совпадения прежнего содержимого клетки со ссылкой удаляемого объекта нет. Флаг шаблона 40000, использованный при начальной регистрации, не заменяет эту проверку.

Затем настоящий вызов **6877 → 6885** выбирает шаблон и структуру владельца по OBE[3]. У владельца используются:

| Смещение | Использование в этом участке |
| --- | --- |
| +5 | Абсолютный указатель начала выделенной области |
| +9 | Относительная ссылка конца активной цепочки |
| +0E | Относительная ссылка текущего начала обхода |

В C# OriginalObjectChain хранит все три значения относительно начала пула. Указатель +5 преобразован в BaseReference; это не ссылка на первый живой объект после каждого удаления. Ссылки по-прежнему используют исходный ненулевой сдвиг загрузчика.

Четыре ветви функции:

1. Удаляемая запись совпадает с курсором, следующая ещё не конец: курсор переходит на следующую.
2. Удаляемая запись совпадает с курсором и последняя: конец и курсор сбрасываются к исходному началу выделенной области.
3. Запись после курсора и последняя: конец становится ссылкой удаляемой записи.
4. Запись после курсора и не последняя: u32 **предыдущая[0x10]** увеличивается так, чтобы перескочить удаляемую запись.

Записи не уплотняются, их координаты/состояния не обнуляются и память не освобождается. На исходном файле u32+0x10 служит длиной последовательной записи; после удаления в runtime это расстояние до следующей активной записи и может перескакивать сохранённые байты нескольких объектов. Повторно разбирать такой пул как исходный OBE с обычными длинами нельзя.

Счётчики в структуре по `[6BA] + owner × 1A35` изменяются так:

- нет бита DAT[0x40]&8: увеличить u32 по **+19F9**;
- бит 8 есть, бита 20 нет: увеличить u32 по **+19F5**;
- оба есть: оставить оба счётчика.

Переполнение u32 сохраняется. Назначение счётчиков ещё не установлено; они не названы золотом, населением или количеством смертей. Это только два исходных поля в OriginalRemovalCounters.

API поддерживает корректную монотонную цепочку с объектом, достижимым от текущего курсора. Перед очисткой проверяются ссылки и границы. Нативный поиск предшественника таких защит не имеет. Функция сама не определяет момент смерти, проигрыш при гибели героя, порождение эффекта и освобождение записи для повторного использования. Например, вызывающий код **CA17..CA41** обрабатывает своё состояние и возможный эффект до вызова 98CC. Этот внешний жизненный цикл ещё требуется перенести.

## Проверка и воспроизведение

[verify_spatial.py](../tools/verify_spatial.py) проверяет SHA-256 исходного EXE, загружает настоящий код и таблицу направлений из LE, допускает только указанные участки потока управления и прекращает ошибочные/слишком долгие исполнения. Для удаления функция исполняется до ret; для движения — до границы 725C. Никакие вызовы не подменены. Результаты сохраняются как параметры и хэши в [синтетическом эталоне](../tests/fixtures/spatial.json), без исходных байтов игры.

Проверены:

- **104 448** шагов: все 256 значений байта +26 и остатки 0..32 для согласованных направлений; отдельно 64 сочетания направлений, три размера, четыре значения слоя, две фазы координат, пустые/чужие клетки. Сравниваются полная запись, флаг, расстояние, факт переноса и весь буфер трёх плоскостей.
- **25 600** удалений: цепочки из 1/2/3/5 записей разной длины, все достижимые позиции удаления и курсора, базы 1/65537, два владельца, два размера, четыре слоя, четыре маски DAT и OBE, нулевые и предельные счётчики. Сравниваются все байты области записей, три поля цепочки, счётчики и сетка.
- **60** последовательных удалений: цепочки с уже изменёнными ссылками, удаление конца и головы, сброс пустой цепочки. C# совпадает с оригиналом на каждом шаге, сохраняя состояние между вызовами.

Сценовый тест работает с копией настоящего пула первого владельца первой карты и исходной сеткой. Лучнику задаётся контролируемая фаза шага вправо; проверяются перенос занятости, отсоединение с соединением ссылок и отсутствие уплотнения. Затем отсоединяется замок, продвигается курсор и ProbePlacement разрешает освобождённое место. Это проверка связки операций на импортированных данных, а не воспроизведение полного игрового такта или новый режим управления в интерфейсе. Демонстрационные юниты пока используют прежнюю экспериментальную симуляцию.

```sh
python -m pip install -r tools/requirements-research.txt
python tools/verify_spatial.py --game /путь/к/игре --fixture /tmp/spatial.json
dotnet build
godot --headless --path . tests/TestRunner.tscn -- original-spatial
godot --headless --path . tests/TestRunner.tscn -- simulation
godot --headless --path . tests/TestRunner.tscn -- scene
```

Нужен Godot **4.7.2 .NET**, .NET **10 LTS**. Для сцены нужны ресурсы импортёра 10; формат импорта на этом этапе не менялся. Обычные C#-проверки не требуют EXE или Unicorn.

Продолжение: [направление, поворот и подготовка движения](motion-preparation.md) переносит расчёт параметра из DAT/SEG и общую ветвь перед 71F5. Сам поиск пути и внешний такт остаются вне этих участков.
