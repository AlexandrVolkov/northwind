# Анализ загрузчика и логики кадров по исполняемому коду

В образе находятся исполняемый NORWIND.EXE и данные, а не исходные C/C++/ASM-тексты разработчиков. Ниже — восстановление по машинным инструкциям этой версии. Воспоминания игрока и снимки не служат доказательством устройства загрузчика или формул.

## Адреса и воспроизведение

`tools/analyze_executable.py` проверяет известный SHA-256 EXE, находит LE через e_lfanew внутреннего MZ по смещению 217764 и собирает три объекта по таблице страниц. Учитываются непоследовательные физические страницы, неполная последняя страница и нулевой незаписанный хвост объекта. Поддерживаются обычные несжатые страницы; неизвестные кодировки отклоняются. Это статическое отображение без релокаций, не полноценный загрузчик для запуска.

| Объект | Размер | Страниц | Флаги |
| --- | --- | --- | --- |
| Код | 0x23dc2 | 36 | 0x2045, 32-битный |
| Данные | 0x3e00 | 3 | 0x2043 |
| Дополнительные данные | 0xf189 | 16 | 0x2043 |

Далее все адреса инструкций — **смещения внутри первого объекта**, а не физические смещения EXE и не линейные адреса процесса. Полный индекс с хэшами, отображением страниц, шаблонами и присваиваниями FS: [code-analysis.json](code-analysis.json).

```bash
python tools/analyze_executable.py --game "/путь/к/игре" --output build/code-analysis.json --code-output build/original-code.bin
objdump -D -b binary -m i386 -M intel --start-address=0x3593 --stop-address=0x35a8 build/original-code.bin
```

Извлечённый код сохраняйте только локально, например в игнорируемой папке build. Скрипт не изменяет оригинальные файлы и не применяет патчи.

## Установленная цепочка DAT → WRK

1. EXE 0x3570 задаёт имя DAT. После чтения файла 0x3593 читает первый u16, 0x3596 прибавляет к базе **2**, 0x3599 сохраняет начало записей; 0x35a1–0x35a5 делит размер таблицы на **171**.
2. 0x35ac задаёт имя WRK, 0x35b9–0x35bf сохраняет адрес прочитанного WRK в поле +9 записи армии.
3. Цикл объектов 0x430e–0x4328 выбирает армию через OBE[0] со stride 0x56, затем шаблон через OBE[0x0e] со stride 0xab. В EDI получается указатель настоящей записи DAT.
4. 0x433a прибавляет **DAT[0x3b]** к базе WRK; 0x4343 устанавливает AH=1, 0x4346 вызывает вычисленный адрес. После возврата 0x434d–0x4350 копирует байт состояния OBE[0x19] в OBE[0x1a].

Для всех 123 шаблонов смещения обработчиков находятся внутри соответствующих WRK. У замка ARMY__02.DAT: индекс 2, физическое начало записи **344**, WRK entry **0xfe**. Обработчик при AH=1 переходит на WRK+0x157; по 0x179 вызывает FS:0x41. Инициализация EXE по 0x2921 записывает в этот слот **0xc88c**.

Блок EXE 0x28a9–0x2cd7 состоит из 107 последовательных инструкций `mov dword ptr fs:[slot], value`. Инструмент разбирает именно этот блок, а не ищет похожие байты по всему файлу. Значения и типы других целей требуют проверки мест использования; весь список не объявляется набором восстановленных функций.

WRK вызывается из 32-битного кодового объекта через near-call. Префикс 67 у обращений FS переключает адресацию операнда на 16-битную. Он не означает, что весь WRK исполняется как 16-битный код. В обработчиках есть встроенные таблицы относительных переходов; декодирование каждой последовательности байтов как инструкций даёт ложные функции.

## Исправление импорта DAT

Ранее границы записей считались от нуля. Имена, размеры изображения и базовые кадры при этом читались с правильных абсолютных позиций, но raw_record_hex включал два байта перед записью и терял последние два байта самой записи.

Импортёр 7 начинает записи с 2, сохраняет заголовок отдельно, экспортирует настоящий file_offset/template_offset и поле wrk_entry_offset. Относительный указатель имени находится по +7 настоящей записи. `templates.json` теперь версии 2; нужно повторить импорт. Полное восстановление исходника проверяется как `header + records + tail`.

## Расчёт кадров замка в оригинальных инструкциях

Функция 0xc88c продолжает работу по 0xc8e0 с параметрами из DAT. Это не простой выбор кадра по проценту здоровья: учитываются текущий кадр, предыдущее значение состояния, направление изменения и фаза обновления.

У замка прочитаны:

| Поле настоящей записи DAT | Значение | Использование инструкциями |
| --- | --- | --- |
| +0x45 | 127 | Знаменатель расчёта после прибавления 1 |
| +0x48, u16 | 876 | Начало диапазона |
| +0x4a | 8 | Размер начального диапазона и множитель после прибавления 1 |
| +0x4b | 1 | Размер следующего диапазона |

В рассматриваемой ветви `lo=876+8=884`, `hi=885`. По 0xc965–0xc97f для изменившегося байта `s=OBE[0x19]` вычисляется **q=floor(s×9/128)**. При уменьшении состояния целевой кадр равен **892−q** с дополнительными проверками текущего кадра; при q=0 байт состояния становится FF. При увеличении используется другая ветвь, способная выбрать кадр **876+q**; она также сохраняет определённые текущие кадры. Перевод сохраняет исходные 8/16/32-битные операции и проверки, а не заменяет их линейной интерполяцией.

OBE[0x19] пока называем байтом состояния. Формула не устанавливает, как он связан с показываемыми игроку очками здоровья, оплатой ремонта или прогрессом строительства.

## Проверка исполнением x86

`tools/verify_building_frames.py` исполняет оригинальные инструкции **0xc8e0..0xc9fd** в Unicorn 2.1.4 и сравнивает результат с явным переводом ветви на Python. Диапазон входов: s=0..127, предыдущее состояние 0 или 127, текущий кадр 876..892. Получены **4352 случая, 0 расхождений**. Отчёт и примеры: [building-frame-check.json](building-frame-check.json).

```bash
python -m pip install -r tools/requirements-research.txt
python tools/verify_building_frames.py --game "/путь/к/игре" --output build/building-frame-check.json
```

Ограничения эксперимента заданы явно: OBE[0x14]=0, OBE[0x0f]=0, нечётная фаза счётчика; сравниваются только кадр OBE[1:3] и состояние OBE[0x19]. Вызов создания эффекта 0x9727 пропускается. DOS, полный игровой цикл и обработчик WRK целиком не исполняются. Проверка не подтверждает скорость, стоимость ремонта, формулы урона, эффекты или полную обработку смерти.

Например, уменьшение состояния 127→71 с кадра 884 даёт 888; уменьшение до 14 даёт кадр 892 и FF. В другом входном состоянии увеличение 0→113 с кадра 888 даёт 883. Поэтому преждевременно реализовывать ремонт простым обратным проигрыванием кадров повреждения.

Далее восстановлены общий шаг увеличения OBE[0x19] со счётчиком и списанием трёх запасов, а также хвост применения повреждения. Обе операции перенесены в C# и проверены против x86 на 199 680 комбинациях: [building-condition-kernel.md](building-condition-kernel.md). Ещё требуются запуск действия из интерфейса, начальное состояние, назначение ресурсных слотов и полный цикл WRK/эффектов.
