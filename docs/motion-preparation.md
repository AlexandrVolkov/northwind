# Направление, поворот и подготовка движения по EXE

[OriginalMotionPreparation.cs](../scripts/OriginalMotionPreparation.cs) переносит выбор направления **9688..96CC**, один шаг поворота **9653..9687**, чтение параметра движения **7180..71F5** и их продолжение **7165..725C**, включая выход незавершённого поворота на **72D8**. Движение после подготовки выполняет ранее перенесённый [OriginalSpatialRules](spatial-movement-removal.md).

Это следующие ограниченные участки оригинального исполняемого кода, а не восстановленный целиком поиск пути или такт игры. Новая логика пока не заменяет демонстрационную симуляцию в интерфейсе.

## Направление к точке

9688 вычисляет беззнаковые разности исходных u32-координат, определяет знак отдельно по сравнению и выбирает сектор из таблицы **DS:19D7**, LE-объект № 2. При сильно различающихся смещениях сравнивается удвоенная меньшая компонента с большей. Арифметика удвоения сохраняет переполнение u32; замены на atan2 или нормализованный вектор нет.

Таблица для `x_sign × 3 + y_sign`, где индексы знака — 0/1/2 для отрицательного/нулевого/положительного смещения:

```text
7 6 5
0 FF 4
1 2 3
```

Y растёт вниз; 0 — вверх, 2 — вправо. Совпадающие координаты возвращают **FF**, а не направление 0. Это особый результат данной функции: вызывающий код обязан обработать его в своём контексте, а не объявлять найденным маршрут.

## Поворот на один сектор

9653 получает целевое значение в AH и текущую сторону в младших трёх битах **OBE[0x25]**. Если они равны, запись не меняется и возвращается ZF=1. Иначе разность маскируется семёркой, и сторона изменяется на один сектор. При расстоянии ровно четыре сектора выбирается увеличение индекса. Новое кодирование: `u8(target << 3) | next_direction`.

Исходная функция сравнивает входной байт целиком до маскирования разности. Поэтому C# сохраняет поведение и для значений вне 0..7; тесты включают старшие биты. Это не утверждение, что интерфейс позволяет выбрать такую сторону.

Кадр рассчитывается с существенным ограничением разрядности:

```text
frame = u16(u8(next_direction × DAT[0x4a]) + u16(DAT[0x48]))
```

После MUL код обнуляет AH, то есть отбрасывает старший байт произведения перед сложением. `TurnToward` возвращает именно **исходный ZF**, а не «направление достигнуто». На ветви изменения стороны ZF определяется последним сложением кадра. Если результат кадра равен нулю, вызывающий участок продолжает движение, даже если сравнение сторон ранее не совпало. Эти редкие комбинации проверяются, а не исправляются по предположению.

Для обычных ненулевых кадров достижение нужной стороны возвращает незавершённый поворот; только следующий вызов с уже равными сторонами получает ZF=1 и начинает шаг. Метод `TurnAndAdvance` сохраняет этот дополнительный вызов.

## Параметр из карты и DAT

7180 получает клетку через сдвиг координат на 5. Если **OBE[0x0d]&1 != 0** и клетка **нулевой плоскости занятости** ненулевая, выбирается DAT[0x58] с нулевой поправкой, без чтения MAP/SEG. Иначе читается младший u16 тайла MAP, затем первый байт его 8-байтовой записи SEG. Следовательно, изменение нижней плоскости может влиять на подготовку движения; её игровое название этим не установлено.

Для байта свойства `p` выбирается `v = DAT[0x58 + (p & 7)]`. Если бит **80** в v отсутствует, выполняется байтовое вычитание `v -= p >> 4`. Если бит установлен, вычитание пропускается. Затем:

```text
OBE[0x26] = u8((OBE[0x26] & C0) | (v & 3F))
OBE[0x26] = u8(OBE[0x26] + (OBE[0x16] >> 5))
```

Поле +26 — упакованное значение с дробным накоплением, а не напрямую число пикселей за кадр. Назначение полного байта +16 ещё не определено; перенос использует только подтверждённое чтение его старших трёх битов. Сохранены переполнения при вычитании/сложении.

Те же восемь DAT-значений используются ранее перенесённой проверкой строительства как маска «ноль/неноль», но подготовка движения использует их численно. Названия классов местности и остальные свойства SEG этим не восстановлены.

`InitializeAccumulator` поддерживает координаты в границах сетки. При чтении карты проверяются её размер и наличие используемого байта свойства. На ветви с занятой нулевой плоскостью чтение MAP/SEG, как и в оригинале, пропускается. Повреждённые данные/координаты вне карты не объявляются совместимыми; исходный участок не имеет этих защит.

## Связка с шагом

`TurnAndAdvance` очищает бит 40 исходного флага по 1C9F, вызывает настоящий перенесённый расчёт поворота и при ZF=0 возвращает pending без подготовки/изменения координат. При ZF=1 увеличивает байт **OBE[0x24]**, подготавливает +26 и продолжает движение до границы 725C. Сохранены изменения записи, флага и всех трёх плоскостей занятости.

Вход — уже выбранный шаг маршрута и подготовленные глобальные размеры области. Код не создаёт маршрут по щелчку пользователя. Другие ветви выбора действия, столкновения, частота тактов, анимация, звук и завершение шага после 725C требуют отдельного переноса. Продолжающееся движение в состоянии 4 входит в 71F5 без повторного поворота и подготовки; нельзя вызывать `TurnAndAdvance` на каждом таком обновлении вместо `AdvanceMotion`.

## Эталон и проверки

[verify_motion_preparation.py](../tools/verify_motion_preparation.py) исполняет исходные инструкции под Unicorn с проверкой версии EXE и ограничением адресов/числа инструкций. Таблицы направлений берутся из настоящего LE-объекта данных; вызовы поворота и переноса занятости не подменены. Синтетический [эталон](../tests/fixtures/motion-preparation.json) содержит параметры, исходный SHA-256 и хэши результатов, без оригинальных байтов.

| Проверка | Случаев | Сравниваемый результат |
| --- | ---: | --- |
| Направление к точке | 50 625 | Байт направления; координаты включают границы u32 и пороги соотношений |
| Один шаг поворота | 107 520 | Полная запись и ZF; все 256 исходных кодов, 35 целей, три базы, четыре множителя кадра |
| Подготовка DAT/SEG | 107 776 | Полная запись; все 256×256 пары базового параметра и свойства плюс слои, занятость, перенос старших битов и поправка +16 |
| Продолжение 7165 | 17 280 | Выход pending/продолжение, запись, флаг, расстояние, перенос занятости, полные три плоскости |

Всего **283 201** сравнение C# с x86 без расхождений. Сценовый тест использует копию исходного лучника первой карты и реальную MAP/SEG/DAT: выбирается направление вправо, поворот проходит через кадры **602** и **613**, следующий вызов подготавливает значение **8** и перемещает объект на **2** единицы. На этой фазе порог переноса клетки ещё не пересечён. Это контролируемая фаза на исходных данных, не запись полного такта оригинальной игры.

```sh
python -m pip install -r tools/requirements-research.txt
python tools/verify_motion_preparation.py --game /путь/к/игре --fixture /tmp/motion-preparation.json
dotnet build
godot --headless --path . tests/TestRunner.tscn -- original-motion
godot --headless --path . tests/TestRunner.tscn -- simulation
godot --headless --path . tests/TestRunner.tscn -- scene
```

Нужен Godot **4.7.2 .NET**, .NET **10 LTS**. Для обычных C#-проверок EXE/Unicorn не нужны. Готовые ресурсы в репозитории уже содержат используемые необработанные DAT и свойства SEG: формат импорта не менялся, повторно импортировать ISO не требуется.

Проверка кандидата перед движением теперь перенесена отдельно: [7C63/7D4C, полная область, слои и опорные объекты](movement-admission.md). Сам исходный планировщик и обработка контактов ещё не подключены.
