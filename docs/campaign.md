# Карта похода оригинала (C12, готово для проверки)

Адреса кода — LE:1. Это исследование исходного EXE и раздела 99h
сохранения, а не реконструкция по одному снимку экрана. Сырые SAV и
EPI в репозиторий не добавляются.

## Файлы EPI и топология

`1A24E..1A27B` подставляет выбранное восьмисимвольное имя (`game` или
`demo`) в строку `.epi` и вызывает `1C399`, который читает до 512 байт
файла через DOS `int 21h`. Сразу после этого код использует первые
два байта как width/height и выделяет `0x841×width×height` памяти.
В другом пути `196E1..196F9` копирует ровно `0x160 = 16×22` байт
из `AFC2`, то есть с отступа 6 от начала EPI. Длина всех трёх файлов
строго равна `6 + 16×22 + width×height + preload_count`, где
`preload_count` — байт заголовка `+4` (в образцах 5). Разметка в
`tools/episode_source.py` сохраняет неизвестные байты, 16 имён CP866
с двумя байтами стартовой области, сетку area ID и список предварительно
загружаемых ID;
готовый результат — `data/original_episodes.json`.

| EPI | Сетка | ID областей по строкам | Первые три имени |
|---|---:|---|---|
| GAME | 4×3 | 1,2,3,10 / 4,5,6,10 / 7,8,9,10 | Олег, Игорь, Эйрик |
| DEMO | 1×2 | 21 / 22 | Илья, Александр, Эрик |
| DEMO2 | 1×1 | 22 | Олег, Игорь, Эйрик |

Сетка GAME подтверждает девять основных ID и повторяющийся ID 10 в
четвёртом столбце. На диске есть `MAP_10.MAP` и `SCENA_10.SCN`.
Загрузчик `3396..33D2` читает EPI в `[1CC5]`, вычисляет
`[1E2B] = [1CC5] + 0x166` — начало таблицы area ID. При загрузке
области `3321..3348` берёт индекс `Y×width+X` и записывает
`[1E2B+индекс]` в `[1EC5]`; это прямое доказательство, что значения
сетки задают ID файла области. Код `33D8..34B4` отдельно перебирает
`preload_count` байтов после таблицы, в наших EPI это `0,1,2,3,5`,
и подставляет их в имена ресурсных файлов. Эти байты не являются
продолжением сетки.
Два байта после каждого имени — **координаты стартовой области**:
для Олега `(0,0)`, Игоря `(0,2)`, Эйрика `(2,2)`. При начале новой
игры `312D..315F` берёт `EPI[6+22×выбранный_герой+20/21]` и пишет
их в `[1CC7]/[1CC8]`, затем загружает ID из сетки. Байт заголовка
`+5` используется `1A17F/1A3F7` как число активных участников (7 у GAME/DEMO,
8 у DEMO2).

## Память мира и видимый фрагмент

`1A24E..1A3E2` выделяет под состояние мира `0x841 × width × height`
байт, где width/height считываются из `[AFBC]/[AFBD]`. Формат одного
блока: первый байт флагов, затем 16 записей по `0x84` байта
(`1 + 16×0x84 = 0x841`). Эти байты сохраняет раздел 99h, см.
[save-format.md](save-format.md). В имеющемся SAV сетка 4×3 и 12
блоков. Экран `1A14E..1A21F` показывает окно 3×3: по три блока в
строке с шагом `0x841`, затем пропускает четвёртый блок. Таким образом
видимое окно и размер хранилища мира различаются. Реальные доступные
миссии и смысл всех 12 мест пока не установлены.

Для каждого видимого блока `1A3E3` вызывает создание флажков, только
если установлен бит 0 заголовка и `[AFC1]` (число участников) не ноль.
`1A40B..1A54B` идёт по 0x84-байтным записям и проверяет показатель
`+17h > 0x7CF` и другие поля до вызова `1A553`/`1A60A`. Порог
не следует без дополнительного доказательства называть населением.
Граф участка `1AA12` был построен в локальном `build/campaign-window-graph.md`:
отрисовка вызывает `1AB11`, `1AB2A`, `1AC2C`; вне диапазона остаются
проверка указателя, вывод текста, WORK/HISTORY blit и прочие помощники.

## Запись флажка и окно поселения

`1A553..1A609` преобразует запись участника в виджет флажка. Из
записи `+15h/+16h` берутся координаты в шкале карты и пересчитываются
в область 448×384 через `1A22F` (умножение, затем деление). К ним
добавляются `(86,12)`. Размер виджета — 16×16, обработчик — `1AA12`.
Строки имени и заголовка берутся по `+23h` и `+37h`, а байт портрета
по `+22h`. Для местного участника виджет получает флаг `80h`, для
другого — 0. Исходный `+1Ch` (u32) копируется в виджет `+22h` и
печатается после «Население : »; исходный `+1Bh` (u8) — в `+26h`
после «Постройки : » (`1ABEA..1AC23`). Остальные копии из `+4Bh`,
`+4Fh`, `+53h` ещё без проверенного названия.

`1AA12` реагирует на события 0/1/2. При нажатии флаг выделения
(`widget+21h`, бит 0) включается и указатель сохраняется в `[C94F]`.
Повторный клик закрывает окно и обнуляет `[C94F]`; бит 7 сохраняется.
Отрисовка вызывает `1AB2A` для окна 250×150 либо `1AC2C` для 250×200,
если установлен бит 7. Изображения — HISTORY.SPR 50/51; портрет —
WORK.SPR `0xC3 + [widget+20h]`. Подписи «Население : » и
«Постройки : » находятся в LE:3 `C953`/`C960`; именно их печать
подтверждает названия полей `+1Ch` и `+1Bh` записи.

`1A60A..1A69A` создаёт отдельный 16×16 виджет **предводителя**
(обработчик `1A901`) из `+20h/+21h` записи, с центром в той же области
карты. Это подтверждает `10DCB..10DF1`: обновление мира вызывает
`1ECA0` с маской `F08h` и значением `F00h`, находит соответствующий
объект и пишет его пиксельные координаты, делённые на 32, в
`+20h/+21h`. Среди всех 123 шаблонов фильтру подходит только
`ARMY__02.DAT` №20 «Предводитель» (`flags=200F00h`). Флаг
поселения и маркер героя создаются разными путями. Сами флажки
берутся из памяти мира, которую также пишет раздел 99h SAV.

`10CA0..10E18` обновляет 0x84-байтные записи области из текущих
участников перед сохранением: выставляет бит 0 заголовка блока,
копирует 16 отношений в `+1..+10h`, имя участника в `+23h`,
название поселения в `+37h`, портрет в `+22h`, показатель силы
из блока ИИ `+19F1h` в `+17h`, число построек из `+5Ch` в
`+1Bh`. Счётчик населения виджета `+1Ch` берётся из участника
`+24h`. Позиции флажка `+15h/+16h` приходят из блока ИИ
`+61h/+62h`, а маркер предводителя — из найденного объекта.
Это доказывает происхождение основных полей после загрузки сценария;
первоначальные значения блока ИИ и условия изменения остальных
счётчиков требуют отдельной трассировки.

Полная карта **записываемых диапазонов** одной записи `84h` следует
из `10CD5..10DF8`; смещения ниже указаны от первого байта записи,
сразу после флага блока. Для неизвестных полей сохранён адрес
источника без придуманного игрового названия.

| Смещение записи | Размер | Источник в памяти | Подтверждённый смысл |
|---|---:|---|---|

| `22` | 1 | участник `+B8` | портрет |

## Переход в соседнюю область

`10799..107E8` получает индекс направления, читает пару смещений
`dx/dy` из LE:2 `19C7/19C8`, складывает её с текущими координатами
`[1CC7]/[1CC8]` и передаёт полученные X/Y в `103EC` вместе с
координатами размещения объекта на новом краю. `103ED..103FF`
отклоняет X≥ширина или Y≥высота. Важная деталь: проверка использует
размеры **4×3 из EPI**, поэтому четвёртый столбец GAME с ID 10 не
отсекается самой проверкой границ.

Если сохранённой записи целевой области ещё нет, `104F5..10565`
вычисляет `ID = [1E2B + Y×width + X]`, подставляет его десятичные цифры
в имя `SCENA_nn.SCN` и читает исходный сценарий. Следовательно,
четвёртый столбец действительно ссылается на файл `SCENA_10.SCN`.
`10573..105EE` затем создаёт или ищет раздел 22h для целевой области
с тегом из координат X/Y; связь с форматом SAV описана в
[save-format.md](save-format.md). Успех переноса зависит также от
размера файла сценария и вместимости раздела 22h; доступность
каждого входа в ID 10 и правило переноса группы ещё не доказаны.

Обычное движение текущего участника вызывает эту ветвь в
`92F1..9342`. Координаты объекта переводятся из пикселей в клетки
сдвигом на 5. На границе выбирается направление в порядке:
верх (`y=0`, индекс 0), лево (`x=0`, индекс 6), низ
(`y+1≥высота`, индекс 4), право (`x+1≥ширина`, индекс 2).
`D12C` читает младшие три бита типа клетки под объектом; при
значении 1 переход пропускается. Затем `10799` вычисляет соседнюю
область и координаты высадки. Эта ветвь проверяет владельца
`object[3] == [1972]`, но не проверяет здесь, что объект — герой.

Внутри `103EC` переносится **одна** запись объекта: копия во временный
буфер `[2139]`, поиск или создание раздела SAV 22h целевой области,
проверка ёмкости этого раздела и запись копии (`10573..10695`).
После успешной записи исходный объект обрабатывается отдельно
(`10762..1078D`). Если у его шаблона DAT поле `+40h` имеет
`flags & 0F00h == 0F00h`, ветвь `1069A..10756` дополнительно
сохраняет текущие координаты в записи участника и ставит `[1EC6]=1`.
Проверка всех 123 встроенных шаблонов по исходным DAT показывает
ровно один такой флаг: `ARMY__02.DAT`, шаблон 20 «Предводитель»,
`flags=200F00h`. Значит, успешный переход героя запускает смену
области, а обычный юнит переносится как отдельный объект без смены
игрового экрана. Автоматического прохода всей выделенной группы
через один вызов `103EC` в этом участке нет.

При записи в `103EC` нет проверки занятости клеток высадки:
`36F0` читает размер файла сценария, а `10611..10653` проверяет
место в разделе 22h. Проверка происходит **после открытия области**.
`10802..109E7` перебирает записи раздела 22h, подрезает координаты
у края в `1093B..10960` и для обычных объектов вызывает `10AD2`.
Этот помощник ищет место вокруг желаемой точки: выравнивает её по
сетке 32 пикселя, перебирает кандидатов в расширяющемся квадрате,
отбрасывает выходы за внутреннюю границу 32 пикселя и вызывает
`AC63` для проверки размещения (`10B32..10B65`). Если подходящего
кандидата не нашлось, `10984` пропускает восстановление объекта.
Такой двухэтапный путь согласуется с наблюдением игрока о занятом
крае; точное правило «четыре клетки глубиной» ещё не установлено.

## Что осталось выяснить

- Первоначальные значения полей блока ИИ, которые `10CA0` переносит
  в 0x84-байтные записи мира.
- Правила допуска перехода героя и сопровождающих войск; конкретные
  входы в повторяющийся ID 10.
- Путь вызова экрана итогов миссии.
- Подтверждение значений счётчиков флажка на живом экране оригинала.

## Подготовленная модель C#

`scripts/OriginalCampaignTopology.cs` читает готовый
`data/original_episodes.json` и даёт стартовую область участника,
ID области по X/Y, соседние координаты по восьми направлениям из
LE:2 `19C7` и пиксельную точку прибытия для четырёх сторон по
LE:1 `10799..107D7`. `tools/verify_campaign_arrival.py` исполняет
`10799..107E8` под Unicorn на 160 случаях, подменяя только вход
в `103EC` и сохраняя переданные ему область и пиксельную точку.
Фикстура — `tests/fixtures/campaign-arrival.json`, без машинных байт.
Режим `original-campaign` проверяет все 12
ячеек GAME, старт трёх героев, край сетки, обе демосетки и
координаты прибытия, в том числе диагональные индексы исходной
таблицы (в формуле `10799` для них действует горизонтальная ветвь).
Эти методы пока не подключены к экрану карты
или игровому циклу; проверка переноса объектов остаётся задачей C12.

## Статистика итогов

`1AE0C..1B091` содержит рисовальщик окна 250×200 (HISTORY.SPR 51,
портрет WORK.SPR `0xC3 + [widget+20h]`). Строки LE:3 `C96D..C9C4`
заканчиваются байтом `FFh`. В нём есть заголовки «Ваши потери» и
«Потери врага», после каждого — числа с подписями «Население : » и
«Постройки : ». Числа берутся из полей виджета `+2Eh/+32h` и
`+38h/+3Ch` соответственно (`1AED4..1AF4E`). Ниже расположен блок
«Добыто» с тремя значками WORK.SPR 311, 313 и 312 и числами из
`+22h/+2Ah/+26h` (`1AD2D..1AE03`, `1AFBD..1B08E`). Также есть
«Уничтожено», «Наций», «Варварских поселений» и «Порабощено наций»;
для последних трёх выводятся `+36h` u8, `+37h` u8 и `+40h` u32.
Строка «Предметы» лежит рядом в LE:3 `C9C4`, но статической ссылки
на неё в этом рисовальщике не найдено.

Статической ссылки на вход `1AE0C` в трёх LE-объектах тоже пока не
найдено. Это доказательство существования кода и раскладки, но ещё
не доказательство достижимости окна в обычной игре. Значения полей
виджета и момент его создания остаются открытыми.

## Кандидат на завершение похода

`110C8..1114F` проходит все блоки мира (`[3E87]`, шаг `841h`) и
считает блоки с битом 0, где не найден живой сильный чужой участник,
отличный от текущего и не имеющий отношения 3/4. «Сильный» здесь
означает только сравнение поля записи `+17h > 1999`, без
дополнительного игрового названия. Если число таких блоков не меньше
7, код проверяет первый 0x84-байтный слот блока с индексом 2
(`3E87+1082h`: в GAME координаты `(2,0)`, ID 3). При установленном
бите блока и поле `+17h ≤ 1999` он ставит `[1EC6]=3`, что главный
цикл обрабатывает как завершение (`3221..32B9`, см.
[save-format.md](save-format.md)).

Статического вызова `110C8` не найдено ни в одном из трёх LE-объектов.
Поэтому пока нельзя утверждать, что это достижимое условие победы,
а также связывать его с драконами или картой 10. Граф процедуры
`build/campaign-completion-graph.md` построен локально; внешних
вызовов у неё нет.
