# Кнопка ремонта, очередь действия и новая постройка

Продолжение [разбора операций состояния](building-condition-kernel.md). Выводы получены из EXE, DAT и WRK. Новая реализация C#: [OriginalBuildingLifecycle.cs](../scripts/OriginalBuildingLifecycle.cs); импортёр 8 экспортирует описания кнопок и начальные параметры из DAT в templates.json версии 3.

## Описания команд из DAT

От начала настоящей записи шаблона по +0x0b расположены **шесть записей по 8 байт**. EXE 0x6ec1–0x6f17 выбирает их в зависимости от битов OBE[0x0f] и формирует таблицу панели:

| Смещение внутри записи команды | Поле |
| --- | --- |
| +0, u16 | Кадр значка |
| +2, u32 | Относительный указатель от самого поля на заголовок подсказки |
| +6, u8 | Режим обработки нажатия |
| +7, u8 | Код, сравниваемый при объединении команд выделенных объектов; смысл сохраняется как raw_group |

Подсказка начинается с u16 **скан-кода горячей клавиши**, затем идут текст CP866 и терминатор FF. EXE 0x6ef8–0x6f04 указывает на текст после этого заголовка и читает клавишу по text−2; по 0x619e–0x61ab она сравнивается с вводом. Заголовок не является ID команды. Его младший байт тоже может быть FF, поэтому искать терминатор нужно после двухбайтового заголовка.

Текст содержит двухбайтовые escape-последовательности `7e,style`. Их пропуск подтверждён EXE 0x7028–0x702f. Импорт сохраняет полный raw_tooltip_hex вместе со стилями и отдельно выводит читаемую подпись. В шести DAT найдено **233 непустых описания**; отсутствующие записи также сохраняются со своим номером и необработанными байтами. Наличие описания не означает доступность кнопки во всех состояниях объекта.

Для замка ARMY__02.DAT[2]:

| Слот | Подпись | Кадр | Режим | Скан-код |
| --- | --- | --- | --- | --- |
| 0 | Отмена | 872 | 0 | 0x24 |
| 1 | Ремонт | 873 | 0 | 0x23 |
| 2 | Выбор | 874 | 7 | 0x20 |
| 3 | Построить | 875 | 3 | 0x22 |
| 4 | Построить | 875 | 0 | 0x22 |
| 5 | Разрушить | 2865 | 0 | 0xff |

Разные режимы одной подписи нельзя объединять: режим 3 по 0x61f6–0x61fc переходит в отдельный обработчик, а режим 0 применяет команду к объекту непосредственно. Перегрузка QueueDirectCommand с TemplateCommand отклоняет отсутствующую команду и режим, отличный от 0.

## От нажатия «Ремонт» до платного шага

По 0x61c7–0x61d3 из номера слота формируется байт `0x40 | (slot << 3)`. Для одиночного объекта и режима 0 участок 0x623d–0x624f записывает:

```text
OBE[0x14] = (old_state & 7) | 0x40 | (slot << 3)
```

Для ремонта из текущего состояния 0 получается **0x48**, а не немедленно 1. Три младших бита сохраняют текущее действие; номер поставленного действия хранится в битах 3..5. Бит 0x40 учитывается текущим обработчиком при завершении.

После возврата обработчика с ZF=1 EXE 0xc8c9–0xc8df выбирает `(state >> 3) & 7`, обнуляет OBE[0x15], записывает выбранное состояние в OBE[0x14]. При выбранном состоянии **1** также записывает **OBE[0x0f]=1**. В WRK замка состояние 1 выбирает обработчик по +0x1bb, который вызывает FS:0x3d → EXE 0xc80d — уже перенесённый шаг со счётчиком и списанием запасов.

QueueDirectCommand и CompleteCurrentAction воспроизводят эти две операции. Полная проверка выбора, владельца и доступности кнопки остаётся обязанностью будущего интерфейса; групповой путь по 0xb8a2 отдельно не перенесён. Это пока не интерактивная команда в демонстрационном бою.

## Создание записи и начало строительства

EXE 0xa758–0xa86f выбирает шаблон и свободное место в цепочке владельца, обнуляет нужное число байтов и вызывает **настоящий WRK-обработчик с AH=0**. Для замка ARMY__02[2] размер записи равен 49. Из шаблона берутся DAT[0x45]=127 и DAT[0x48:0x4a]=876; эти поля теперь экспортируются как initial_condition и initial_frame. DAT[0] экспортируется как runtime_record_bytes. Они отличаются от кадра по DAT[5], ранее использовавшегося как кандидат превью.

У свежей записи устанавливаются армейский слот, владелец, шаблон, координаты, слой, длина; OBE[0x14]=0x80, OBE[0x19]=OBE[0x1a]=127, кадр 876, OBE[0x20]=FF. Обработчик WRK по 0xfe..0x125 при AH=0 задаёт FF в полях 0x22..0x27. Остальные байты свежего 49-байтового замка остаются нулевыми, включая WorkFlags по +0x0f и счётчик по +0x16.

Затем строительный путь EXE **0xb16a–0xb175** отдельно задаёт:

```text
OBE[0x14] = 0x81
OBE[0x19] = 1
OBE[0x1a] = 1
```

WorkFlags при этом не меняется. У свежей постройки он равен 0, поэтому общий шаг 0xc80d пропускает повторное списание; при входе в ремонт код перехода задаёт WorkFlags=1 и включает платную ветвь. Это не означает бесплатного строительства целиком: **перед созданием** участок 0xb095–0xb0e8 проверяет и списывает начальные затраты. Этот платёж и обновление занятости карты после 0xb176 ещё не перенесены.

CreateFreshCastleRecord реализует только свежую 49-байтовую форму с указанной инициализацией; это не универсальный аллокатор OBE. MarkConstruction воспроизводит три записи строительного пути. Поиск дыр в уже существующей цепочке, ошибка выделения, размещение на карте и другие типы объектов находятся вне области этой реализации.

## Проверка оригинальными инструкциями

[verify_building_lifecycle.py](../tools/verify_building_lifecycle.py) исполняет исходные участки без подмены вызовов. При создании запускается полный путь выделения в пустой цепочке и реальный callback ARMY__02.WRK; проверяется также граница записи и увеличение конца цепочки на 49 байт. Изменения самой карты исключены границей эксперимента.

[Фикстура](../tests/fixtures/building-lifecycle.json) содержит входные сетки и хэши результатов: **1536** постановок команды, **3840** переходов, **972** свежие записи с вариантами строительной отметки. C# совпал на всех **6348** комбинациях. Часть входов синтетическая: слоты армии направлены на одну исследуемую таблицу, а крайние координаты и кадры проверяют ширину полей, а не допустимость размещения в игре.

```bash
python -m pip install -r tools/requirements.txt -r tools/requirements-research.txt
python tools/verify_building_lifecycle.py --game "/путь/к/игре" --output build/building-lifecycle.json
dotnet build
godot --headless --path . tests/TestRunner.tscn -- original-buildings
```

Сохранённая фикстура позволяет запускать C#-проверки без копии игры и Unicorn. Проверка сцены дополнительно связывает импортированную кнопку «Ремонт» с байтом очереди 0x48 и отклоняет подмену команды меню прямым действием. Нужен повторный импорт обновлённым конвертером.

Далее перенесены начальная оплата четырёх запасов и базовая проверка места по свойствам SEG и трём плоскостям занятости: [construction-payment-placement.md](construction-payment-placement.md). Ещё нужны назначение ресурсных слотов, живая карта занятости, дополнительные ограничения и полный цикл WRK с временем, кадрами и эффектами. Демонстрационная сцена остаётся отдельным прототипом.

## Двигатель строителя (LE:1 AFDB из B030, шаг 69FE) — перенесён

Команда 58h замка запускает двигатель строителя: `OriginalBuilder.Run` (`scripts/OriginalBuilder.cs`). Для каждого участка: проверка и списание стоимости DAT[7C,80,84,88] с запасов участника (+18,+1C,+20,+24); проба AD5F; при «свободно» — новый объект A758 (его невозможность прерывает постройку), метка `+14=81h`, `+19=1`, `+1A=1`, регистрация 43E5. Не-линейный шаблон (флаг DAT+40 бит 7 снят) завершается сразу: A6AE(шаблон,1), пересчёт D453, A6AE(0,2) при поддержке участника +2C в 28h..32h. Линейный (мост 7, забор 5, 25) шагает 69FE: шаг по ближней ортогональной оси на размер основания, направление 6996 по таблице арктангенса и DS:19C7, чередование округления байтом [50D]; закончив у цели, завершается. Занятая точка прерывает постройку, кроме участка той же линии в той же точке (он берётся повторно). Участок, отвергнутый ландшафтом, пропускается, но оплачивается.

Сверка: `tools/verify_builder.py` (Unicorn; A758/43E5/A6AE/D453 — записанные заглушки) и `tests/OriginalBuilderChecks.cs`, 3000 случаев (1919 участков, 170 линий; реки, ресурсы, помехи, сбой создания). В схватке `EnemyBuild` вызывает двигатель; участки строятся обычным временем постройки (адаптер), деревья A6AE выполняются по окончании. Остановка движения ИИ: юнит, не сдвинувшийся 10 с, прекращает ход (`NoProgress`, адаптер); приближение к цели не требуется, обходы реки не обрываются.

## Проверка места при создании (AC63, 7B79) и поиск свободного места (10AD2) — перенесены

`OriginalCreationPlacement` (`scripts/OriginalCreationPlacement.cs`). AC63: слой 0..2, основание шаблона вокруг точки (байтовое вычитание половины размера, выход за карту — отказ). Слой должен быть пуст под всем основанием (иначе «занято» с первым найденным объектом); у каждой клетки значение местности `DAT[58+класс]` (бит 7 — как есть, иначе минус класс клетки >> 3) должно быть больше нуля, а на слое 1 клетка воды допускается над несущим объектом слоя 0 (`DAT[40]` бит 1, состояние выше `DAT[46]`, `DAT[3F]` не ниже). 10AD2: квадраты со стороной 1, 2, … (до 15) вокруг точки, в каждом side² случайных точек (9E41 — y, 9E55 — x), у границ карты точки пропускаются; клетка ровно на дальнем пределе считается найденной без проверки (флаг после сравнения). Сверка: `tools/verify_placement.py`, `tests/fixtures/placement.json`, 2500 случаев (1197 мест найдено, 142 «занято»). В схватке `FreeSpot` ИИ использует это вместо колец (бывший адаптер).

## «Можно ли строить здесь» (AF07) и правила дальности (B1EC, B28A) — перенесены

`OriginalBuildCheck` (`scripts/OriginalBuildCheck.cs`). Порядок AF07: проба AD5F (занято допускается только для того же участка линии в той же точке — шаблон с флагом `DAT[40]` бит 7); правило дальности; собственная проверка шаблона (запись WRK, AH=4, ZF=1 — отказ); для линий правило соседей BC2E; клетка должна быть разведана участником (бит в карте тумана `[18DA]` сброшен). Правило дальности B1EC: `DAT[4E]` = FFh — везде, иначе в пределах `DAT[4E]` клеток должен быть свой центральный объект (`DAT[40]` бит 3, состояние выше `DAT[46]`, без флагов 60h); затем B28A: без флага 40h у шаблона, если у участника есть здание класса «замок» (флаги F08h = 508h, состояние выше `DAT[46]`), хотя бы одно должно быть в 800 пикселях. Побочный эффект оригинала: `AL` перед вызовом проверки шаблона — остаток B28A (в записях здесь не используется). Сверка: `tools/verify_buildcheck.py`, `tests/fixtures/buildcheck.json`, 3000 случаев (274 разрешено, 558 дошли до проверки шаблона). В схватке `BuildingSite` ИИ (22FE4) использует это; проверка шаблона и BC2E пока разрешают (адаптер).

## Правило соседей линий (BC2E, BADF, BB26, запись WRK AH=9) — перенесено

`OriginalLineNeighbors` (`scripts/OriginalLineNeighbors.cs`, таблицы — `data/line_neighbors.json`, их выгружает `tools/export_line_neighbors.py` из записей WRK шаблонов с флагом 80h: маска в AH и пары «кадр, маска соседей»). Для каждого из восьми направлений на расстоянии основания (байтовая арифметика, таблица DS:19C7, за картой — пусто) в слое `DAT[77]&3` ищется сосед того же шаблона; шаблон соседа с его собственными соседями (BADF) и обратным направлением должен давать маску (`& 55h`) из таблицы; затем так же проверяется набор найденных направлений самого нового участка. Сверка: `tools/verify_neighbors.py` (настоящие BC2E, BADF, D19C и запись WRK), 3000 случаев, 1315 разрешено. В схватке `BuildingSite` ИИ вызывает правило для линий. Запись AH=4 есть только у шахты (шаблон 6: под местом должна быть руда типа 1 или 2, FS:59 — как залежь при завершении; в схватке это `OriginalMineRules.Initialize`) и у шаблона 19 (не перенесена, разрешает); у остальных шаблонов запись сразу возвращает «разрешено».
